## 一、先回答「先前那 60 秒是针对什么」

代码注释里写着两个原因：

1. 「用户手动交卷后浏览器**已经自己跳到判分页**，我们不该再 goto 一次」
2. 「判分页题多资源多，30 秒不够」

**原因 ② 是真的**（11-28 00:42 日志：`Page.goto: Timeout 30000ms exceeded`）。
**原因 ① 是错的推测** —— 这是我当时凭印象写下的，没验证。

## 二、查日志核实：平台到底会不会自己跳

统计**全部** work 日志：

| 分支 | 次数 | 含义 |
|---|---|---|
| 「判分页已在浏览器中打开」（=等到了） | **1 次** | 且那次是我手工补抓后页面恰好停在 viewExam |
| 空等 60 秒后才走 goto | **5 次** | 平台停在 `ExamMessage.aspx` 不动 |

**结论：平台从不自己跳。那 60 秒每次都在空等，用户感受到的「停很久」就是它。**

## 三、改动

```python
# 改前（空等 60 秒）
deadline2 = time.monotonic() + 60
while time.monotonic() < deadline2:
    if "viewexam.aspx" in page2.url: break
    time.sleep(1.0)
if 还不是 viewexam: goto(...)

# 改后（不空等）
if "viewexam.aspx" in page2.url:
    print("判分页已在浏览器中打开，直接抓取")
else:
    print("主动导航到判分页…")
    page2.goto(review_url, timeout=90_000)
```

**保留**：已经在判分页就直接抓（快速路径）；goto 仍是 90 秒超时。

## 四、风险评估（用户要求「考虑全面些」）

| 潜在后果 | 风险 | 核实结果 |
|---|---|---|
| 判分页没加载完就抓，抓到空 | 中 | `wait_graded()` 会等 `ddTm_` 出现（60s），**已兜底** |
| 平台其实会自己跳，只是慢 | 低 | **实测从不跳**（5 次全空等），已排除 |
| goto 太频繁被风控 | 极低 | 每次练习只 goto 一次 |
| ExamMessage→viewExam 需会话状态 | 中 | 1.6/1.8/1.9/2.2 全走 goto，**都成功** |
| 判分页加载 30s+ | 中 | 保留 90 秒超时 |

**结论：删掉空等是安全的，可靠性由 `wait_graded` + 90s 超时兜住。**
