## 一、两条新纪律（写进项目约定）

### 1. 视频播放问题：先读日志，再查问题

**用户原话**：「以后有关视频播放问题请你查看日志后再去查问题」。

11-07 那次 1317 争议里，我犯了两个错：

- 先"摆证据请你判断"，把**下结论的责任推给用户**，而不是自己读日志定性；
- 依据只有 `clock`（页面墙钟）—— 但 `clock` 是 `m_time` 每秒 +1，
  **视频卡住它也照涨**，根本证明不了画面在播。

**纪律**：

1. 遇到「视频有没有播」类问题，**第一步永远是读日志**（`data/logs/gxks-study-*.log`
   + `data/debug/watch_gxks_*.jsonl` 的逐次采样），不是先猜、不是先问用户；
2. 结论必须由日志自证，证据链固定为：
   `t(currentTime) 是否递增` + `paused/ended` + `updates 上报次数` + `progress 里的平台学时`；
3. 为了让日志能自证，本轮已给 `tick` 补上 `d/paused/ended/hidden` 并在打印里摊开
   （提交 `b49515c` + `0ef0cfe`）。**只加事件字段，不改 `classify`/`plan_action`**，
   播放行为零变化；
4. 改代码一律按全局约定五步：查 → 定方案 → 审方案 → 动代码 → 验证。

### 2. 「改了没效果」先查部署，别急着改代码

11-07 到 11-08 连续三轮反馈（小点还在 / 日志还刷新 / 徽标没出现），
根因不是修复写错，而是**两个 uvicorn worker 同时监听 8301**，

**纪律**：出现「改了没效果」，第一步查
`Get-NetTCPConnection -LocalPort 8301` + 请求 `/` 看页面指纹，
确认跑的是新代码，再谈改代码。

## 三、方向定稿（第 4 项：现在定方向，不改架构代码）

### 核心原则

**「账号 × 课程」是二维的；列表永远是唯一全量视图；详情一次只看一个 (账号, 课程) 组合。**

```
账号表（唯一全量视图，虚拟滚动可插拔）
  └─ 行 = 账号；「课程」列显示该账号 courses（多门折叠，如 32/33）
       └─ 点某账号 → 详情区按 (账号, 课程) 二维切换
            ├─ 进度：默认「只看在跑的迷你卡」(账号·课程·节·x/y)
            └─ 点「展开」才按需加载该账号该课程的完整节列表

日志：默认「全部账号合并流」，每行前缀 [账号/课程]；下拉可过滤
     （页签只作为 ≤5 账号的可选视图，不作为主形态 —— N 大时页签不可用）

课程维度落点（保持现有，扩展时不重写）：
  - 节缓存  sections_<label>_<course>.json   ← 已按 (账号,课程) 分文件，保持
  - 账本    gxks_ledger.jsonl 带 course 字段   ← 已带，聚合按 (account, course) 分组
  - 账号表  accounts[].courses                ← 已支持多课
  - 待办    Q30「平台切课」→ **必须实机验证的阻塞项**，第二个课程样本一到就验
```

### 为什么这个方向能撑到上百账号

- **列表是唯一全量视图**：100 个账号也只是滚动，不试图一屏塞下所有细节；
- **详情按需加载**：只有点开的那一个 `(账号, 课程)` 才读节列表，不预加载 100 份；
- **日志合并流**：唯一随规模退化的形态（页签在 N 大时必然失效）；
- **课程是一等维度**：从缓存文件名、账本字段到 UI 切换都带 course，
  不会出现「多账号同课时进度串在一起」。

### 虚拟滚动扩展入口（现在只定接口，不改代码）

```js
// 现状：renderAccounts(state) 一个函数既算数据又拼 HTML 又 innerHTML
// 定稿后拆成两层（本轮 **不落地**，只写进待办）：
accountRows(state)              // 纯函数：筛选 + 排序 + 组装行数据，返回全量
paintAccountRows(rows, range)   // 只渲染可见区间到 DOM

// 现在：range = 全部（行为完全不变）
// >50 账号：套一层虚拟化，只改 paintAccountRows 的调用方
//           SEL / 筛选 / course / 勾选 逻辑全留在 accountRows 层，一行不动
```

**理由**：把「取数据」与「渲染」拆开，虚拟滚动就退化成"换一个渲染器"，
而不是"重写账号表"。这是最小代价的扩展入口，也符合"改动涉及代码先审影响面"。

### 性能地基（列为待办，20 个账号时就要修）

`_account_cards()` 现在**每个账号都调一次** `gledger.today_totals()` /
`recent_totals()`，而 `ledger.read_rows()` 是**把整个 jsonl 读进内存再逐行解析**。
100 账号 × 每 4 秒 = 每 4 秒读 200 次账本 → 面板卡死。

**待办**：账本**只读一次**、内存按 `(account, course)` 聚合，再分发给各卡片。
纯重构，有测试守护，风险低。
