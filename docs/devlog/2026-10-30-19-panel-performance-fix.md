# 2026-10-30-19 面板性能修复：/api/state 从 6.08 秒降到 0.55 秒

## 一、起因

用户：「面板启动加载出来有点慢，看是否需要优化一下。接下来要安排什么」

## 二、实测定位（先量再改）

| 路径 | 中位耗时 | 字节 |
|---|---|---|
| `/` | 16 ms | 63328 |
| **`/api/state`** | **6078 ms** ← 问题在这 | 9185 |
| `/api/ops` | 16 ms | 4525 |

页面每 **4 秒**轮询一次 `/api/state`，而它要 6 秒 —— 界面等于一直在等。
启动本身另测：**1.15~1.30 秒**（冷启动首次会到 4.3 秒，是字节码编译；见 §五）。

## 三、根因（两次自我纠错）

**第一层：串行探活。** `/api/state` 里对每个账号调一次 `chrome.port_alive()`，
5 个账号串行 = 5 次；`_browser_state` 又探一次 = 第 6 次。每次卡满 timeout(1.0s)
→ 6 × 1.0 ≈ **6078ms**，与实测完全吻合。

**第二层（我一开始判断错了）：以为"是系统代理把 127.0.0.1 也转发了"。**
确实 `getproxies()` 有值、确实该绕代理，但加了 `ProxyHandler({})` 之后**单次探活仍是 1.02 秒**。
于是写探针查真相，实测：

| 探测 | 耗时 | 结果 |
|---|---|---|
| `connect(127.0.0.1, 已关闭端口)` | 1016 ms | **TimeoutError**（不是 ConnectionRefused！） |
| `connect(localhost, 已关闭端口)` | 2016 ms | 先 IPv6 再 IPv4 |
| `connect(127.0.0.1, 活端口)` | 0.0 ms | connected |

**这台机器上"连已关闭端口"不会立刻被拒，而是被丢包挂到超时。**
查防火墙找到三条**全局 Block**（程序=Any、端口=Any）：

```
codex_sandbox_offline_block_loopback_tcp     Outbound Block  TCP  远端端口 1-65535
codex_sandbox_offline_block_loopback_udp     Outbound Block  UDP
codex_sandbox_offline_block_outbound         Outbound Block  Any
```

⇒ 关键结论：**代码不能假设"已关闭端口会立刻被拒"**，探活最坏就是一个 timeout。

**顺带仍然要修的**：`127.0.0.1` 不该走系统代理（本机地址走代理本身就是错的），
虽然它不是这次的慢因。

## 四、改了什么

### 1. `chrome.py`：并发探活 + 更短的 timeout + 绕代理

| 改动 | 理由 |
|---|---|
| 新增 `ports_alive(ports)` **并发**探活 | N 个账号从「N × timeout」变成「约 1 × timeout」，账号再多也不线性变慢 |
| `port_alive` timeout 1.0 → **0.5 秒** | 活着的 CDP 端口本机 0.0ms 握手，0.5s 足够宽松；死端口最坏也就等 0.5s |
| 新增 `_DIRECT`（`ProxyHandler({})`） | 本机地址永远不该走系统代理（正确性，不是性能） |

### 2. `app.py`：一个请求只探活一次

- `/api/state` 里**先并发探活全部端口**，把结果同时传给 `_account_cards()` 与 `_browser_state()`；
- 两个函数都加了可选的 `alive=` 参数（不传时自己探，保持向后兼容）。

### 3. `scripts/run_gxks_multi.py`：删掉自己那份探活副本

它原来有一份**独立的** `port_alive`（timeout=2.0 且没绕代理）→ 5 个账号白等 10 秒。
现在统一 `port_alive = gchrome.port_alive`，一处定义。

### 4. `scripts/fill_profiles.py`：本机 8300 调用绕代理

同类问题，而且它的 timeout 是 **20 秒**，更严重。

## 五、结果

| 项 | 改前 | 改后 |
|---|---|---|
| `/api/state` | **6078 ms** | **546 ms**（**快 11 倍**） |
| `/` | 16 ms | 16 ms |
| 面板启动到可访问 | — | **1.15~1.30 s** |

剩下的 546ms ≈ 一次 0.5 秒 timeout —— 这是当前环境（回环包被丢）的下限。
**没有再往下压**：要做到几十毫秒就得引入"后台线程刷新 + TTL 缓存"，
但状态点晚几秒更新并不影响使用，不值得为它加一份并发状态。已记入待办备选。

## 七、关键决策及理由

1. **并发而不是缓存**：并发直接消除 N 倍放大，且没有"状态可能过期"的代价；
   缓存是第二层优化，收益小、复杂度高，先不做。
2. **timeout 取 0.5 秒**：本机活端口 0.0ms 握手，0.5s 是宽松上限；
   再短（如 50ms）在机器繁忙时可能把活端口误判成"未监听"。
3. **绕代理照改**：虽然它不是慢因，但"本机地址走代理"本身是错的，
   而且代理挂掉时会让探活直接失败。
4. **删副本而不是修副本**：`run_gxks_multi.py` 自己那份探活已经和主实现走偏过一次
   （timeout 不同、没绕代理），统一进口才是根治。
5. **不碰用户防火墙**：那三条 Block 是别的工具留下的，改动系统防火墙风险高、
   与本项目无关；我们的代码改成"不依赖快速拒绝"即可。

## 八、已知边界

1. **每轮轮询仍有约 0.5 秒**（死端口要等一次 timeout）。若想再压，可做
   "后台线程刷新 + TTL"（预计降到 ~20ms，但要加并发状态）；
2. **本机"连已关闭端口会超时"这个环境特性**可能不是每台机器都这样
   （多半与那三条防火墙规则或代理软件有关）——代码已不依赖它；
3. `.dockerignore` / Docker 相关未动。
