## 一、刷新结果：不是「迁移」，是**写回同一个旧文件**（新发现，G-12 升级为 P0）

### 刷新前/后实测

| | 刷新前 18:39 | 刷新后 20:35:11 |
|---|---|---|
| 文件 | `sections_default.json` | **`sections_default.json`（同一个）** |
| `course` | `""` | `""` |
| `pager` | `{6/6}` | `{6/6}` |
| 行数 | 36 | 36 |
| `sections_default_32.json` | 不存在 | **仍不存在** |

**结论：我上一轮说的「点一次刷新即自动迁移」是错的**，当场纠正。

### 根因链（代码级）

1. `page.js refreshSections()` 传 `course: COURSE || STATE.course || ""`。
2. 后端 `/api/sections/refresh` 把 `course` 传给 `gxks_sections.py --course`；
   面板这份缓存 `course=""` → `STATE.course=""` → 卡片 `course_value=""`（实测确认）→ 传空。
3. `gxks_sections.py:162` `course = safe_course("")` → `""` → `sections_cache.path()` 落
   **无后缀** `sections_default.json`。
4. ⚠ **`gxks_sections.py` 全程没有调 `driver.current_course()`** —— 而页面上下拉框明明有
   `value=32`（`run_gxks.py` 日志每次都打印「当前课程 value=32」）。
5. 于是「刷新 → 写回无后缀文件 → 面板 `course_value` 仍空 → 下次刷新再传空」**死循环**。

### 对照：为什么 test 是 `sections_test_32.json`

`run_gxks.py` 用 `driver.current_course()` 拿到 32，按课回写 → test 的文件带后缀。
两条脚本对「课程维度」的处理**不一致**：刷课脚本按课、刷新脚本不按课。

`driver.list_courses()` / `current_course()` / `select_course()`（回读校验）**三件套都在**
（`driver.py:498~563`），Q30 的「结构就绪」属实，缺的是 `gxks_sections.py` 这一处接线。

### 影响（不止格式）

- 甲同学永远只能用无后缀文件 → 将来真有第二门课时，两份课会**互相覆盖**；
- `pager` 字段是旧版 `gxks_sections` 写的，现 `app.py` 已不产出 → 面板会多显示一个分页徽标
  （这就是用户说的「两个账号进度区不一样显示」的第三个成因）；
- 那 3 节 `locked=True` 本次刷新后**仍是 locked** → P-1 需实机看平台是否真未解锁（待用户确认）。

### 建议修法（**未动代码，等用户点头**）

`gxks_sections.py` 在 `drv = GxksDriver(page)` 之后加一行：
`course = course or drv.current_course()`（指定课程优先，没指定就读页面真实值），
后续 `--course` 为空时也能落到 `sections_default_32.json`；`result["course"]` 同步写真实值。
`read_paths()` 已有回落逻辑，旧文件保留但不再被写。改动约 4 行 + 1 条测试。
⚠ 风险：切换后甲同学旧文件不再更新，面板会优先读新文件；需验证 `_pick_sections_cache` 能读到。

## 三、T1 / Q30 与「多对多」：方案给了，**部分落实，核心阻塞仍在**

### 用户当初问的三种关系（devlog `2026-11-08-01` §二）

| 关系 | 结论 | 证据 |
|---|---|---|
| 一个学生多门课（数据） | ✅ 已支持 | `accounts.py` `courses: tuple[int, ...]`；空 = 全部课 |
| 一个学生多门课（调度） | ✅ 已支持 | `run_gxks_multi.py:118-123` 按 `acc.courses` 逐课生成 plan，每课开跑前重算额度（A1：一个账号一个额度池） |
| 一个学生多门课（记账） | ✅ 已支持 | `ledger` 带 `course`，去重键 `course + section_id` |
| 一个学生多门课（**平台切课**） | ❌ **OPEN / 阻塞** | PLAN Q30（L811）：`ddlClass` 只有 1 项 `value=32`、`onchange=""`，切换方式无法证实 |
| 多个学生同一门课 | 🟡 天然不冲突，无样本/无测试 | 各账号独立 Chrome/profile/端口 |
| 面板展示 | ❌ 一次只看一个 (账号,课程) | `/api/state?course=` 只回一份缓存 |

**PLAN §五 数据模型（L138~147）** 早就预留了多对多：
> 「同一批人，但可能是不同学校 / 同校不同专业不同年级，都是多对多的关系」
> → `person ↔ platform_account ↔ (school, major, grade)` 三层，**不是加一列 platform 能解决**。

### 已落地的扩展接口（用户问「有没有留扩展接口」）

| 接口 | 位置 | 状态 |
|---|---|---|

### 结论

**方案给了（devlog 01 §三 + PLAN §7.3.1/Q30），骨架落了大半，但两处没落实**：
① 平台切课（Q30）——**必须等第二门课样本**，不猜；
② 面板多课程查看/切换的**入口虽在，当前 1 门课时被隐藏**，且刷新脚本不写 course（本节一）。

**「先留扩展接口」的做法**：不动平台假设，把①的缺口补上（`gxks_sections.py` 接线），
让单课程也走「按课分文件」这一条路；将来第二门课出现时
`list_courses()` 自动多一项 → 切换器自动出现 → 缓存自动分文件，**不用改架构**。

## 四、G-4 并发口径：三方案（请拍板）

### 三个数字到底是什么（不是矛盾，是三个阶段）

| 值 | 出处 | 语义 |
|---|---|---|
| **1** | `run_gxks_multi.py` docstring「串行（并发 1）」，引 D12 | **核实期约束**（PLAN §7.3.1 / L884：同一出口 IP 多账号同时刷最易被关联，先串行跑稳） |
| **2** | 面板 11-06 加的并发闸默认 | 实现时取的中间值（11-07 两账号验收所用） |
| **10** | PLAN §11.6 `max_concurrency = 10`（10-29 用户暂定） | **产品目标值**，可配改 |

**关键事实**：D12 解除并发的**前置已满足** —— PLAN §7.3.1 L233 写
「并发>1 必须先用零风险实验验掉 Q7/C6（多窗口是否都满足 `hidden=false`）」；
而 L306 记载 **11-07 实测通过**（3 个独立窗口、故意完全重叠、90 秒 `hidden` 全程 False）。

### 三个选项

| 选项 | 内容 | 利 | 弊 |
|---|---|---|---|
| **A（我倾向）** | 认定 Q7/C6 已验 → **并发可配、默认 2**；`run_gxks_multi.py` 去掉「串行 1」硬写，改读同一配置项；PLAN 记「核实期结束，产品并发 = 可配（默认 2）」 | 三处统一、如实反映已验事实、当前 7 账号能直接并发跑 | 2 依旧是保守值，不是 10 |
| **B** | 维持核实期串行 1，面板默认改回 1 | 最保守、完全贴 D12 原文字 | 与 Q7/C6 实测结论脱节；7 账号排队很慢 |
| **C** | 直接上 10 | 一步到产品目标 | ❌ 同 IP 10 会话**未验证** + 本机 4~6GB 内存（PLAN §11.12 自列风险）；L688 明写「不为试探并发上限故意多开诱发验证码」 |

**统一后的权威来源**：`[runtime] max_concurrency`（面板可配），默认 **2**；
`run_gxks_multi.py` 不再自带相反口径。

## 五、T5 日志合并流：方案（请确认）

### 现状（实测代码）

`LOG_LINES` 按 `label|kind` 分桶（**已经分账号存了**），但 `pickLogJob()` 只挑
**一个任务**显示 → 用户看到的是「当前选中账号的日志」，其它账号只有一行提示。
`page.js:2961~2991` 可核。

### T5 方案（devlog `2026-11-08-01` §三 原文）

> 日志：默认「**全部账号合并流**」，每行前缀 `[账号/课程]`；**下拉可过滤**
> （页签只作为 ≤5 账号的可选视图，不作为主形态 —— N 大时页签不可用）

### 具体落地清单

| 步 | 改动 | 风险 |
|---|---|---|
| 1 | 新增 `LOG_MODE`（`merged` 默认 / `single`），工具条加「全部账号 / 单账号」切换 | 低 |
| 2 | 合并流：把 `LOG_LINES` 所有 `label\|kind` 桶按时间归并（SSE 增量自带时间戳则用它，否则按到达序），每行渲染时加 `[账号·课程]` 前缀 | 中：需统一排序键 |
| 3 | 过滤下拉：按 `label` 多选/单选，复用现有 `quickFilter` 样式 | 低 |
| 4 | 保留 `LOG_LINES` 分桶不动（单账号视图仍是它），合并流只是**新的渲染器** → 与 T7「取数据/渲染分层」同一思路 | 低 |
| 5 | `RUNLOG_FOLLOW` / `LOG_ANCHOR` 行号锚点在合并流下按「全局行号」工作 | 中：需回归 11-07 修的滚动不打断 |

**规模理由**：N 大时页签必然失效，合并流是唯一不随账号数退化的形态。
**验收**：两个账号同时跑，日志区能看到带 `[甲同学]`/`[乙同学]` 前缀的交错 tick 行；
下拉过滤后只剩一个账号；往下滚看历史不被挤走。
