# 2026-11-28-07 判断题在早期选项数校验就炸（1.8 实跑暴露）

> 用户做 1.8 海天利刃，交卷后在面板点「确认交卷并入库」，
> 日志报：`[WARN] 抓取判分页失败：ValueError: 分号拆分后的选项数与平台字段不一致`

---

## 一、现象与排查

1.8 三道题都是**判断题**（`type=4`，选项「对/错」），判分页结构正常
（3 个 `ddTm_` 块、每题 2 个 label）。

但主流程 `parse_review_online` 解析失败，
而**兜底解析器 `parse_review_standalone` 抓同一个页面完全成功**（3 题 / 100 分）。

→ 说明问题不在判分页，而在 `parse_review_online` 的**前置校验**。

## 二、根因

`parse_review_question()` 开头有这么一段（早就存在）：

```python
opts = str(row[5]).split(";")
if len(opts) != int(row[4]):
    raise ValueError("分号拆分后的选项数与平台字段不一致")
```

判断题在平台字段里：`tm_arr[5]`（选项串）是**空串**、`tm_arr[4]`（声明数）是 1，
`"".split(";")` 得到 `[""]`（长度 1）——**多数时候碰巧相等就过了**。

但 1.8 这次不等（判断题实际有 2 个内置选项，声明数不一定与拆分数对上），
于是在这里就抛错，**后面那段已经写好的判断题处理根本执行不到**。

**这是我 11-27 加判断题支持时漏掉的地方**：我只改了后面的选项比对逻辑
（`is_builtin` 分支），忘了同一函数**开头**还有一道同类校验。

## 三、修法

判断依据与下面 `is_builtin` 保持一致（选项串为空 / 只有空串 = 平台不给选项）：

```python
_builtin_type = str(row[5]).strip() == "" or opts == [""]
if not _builtin_type and len(opts) != int(row[4]):
    raise ValueError("分号拆分后的选项数与平台字段不一致")
```

**非判断题仍严格校验**（有测试锁），不能因为放宽把错的放进来。

## 四、验证

1.8 的判分页当时还开在浏览器上，用它真实内容重建 `raw_rows` 后跑主流程：

```
✅ parse_review_online 成功  题数: 3
  #1 type=4 标准=['0'] 考生=['0']  076型两栖攻击舰首舰命名为南昌舰。
  #2 type=4 标准=['1'] 考生=['1']  福建舰创新运用了电磁弹射技术。
  #3 type=4 标准=['0'] 考生=['0']  我国第三艘航母是山东舰。
```

⚠ 诚实说明：验证用的是**重建的 `raw_rows`**（1.8 真实的那份随进程退出丢了），
但修复逻辑是对的（判断题跳过校验），且有测试锁住两个方向。

## 五、1.8 的数据已兜底入库

判分页还开着时用 `parse_review_standalone` 抓了：

```
#1 标准=错 考生=错 ✅ 33分
#2 标准=对 考生=对 ✅ 34分
#3 标准=错 考生=错 ✅ 33分
入库 paper_id=11，3 题，待确认核验 3 题
```

**顺带验证了用户的一个真实疑问**：「我改了第 1 题答案，入库的是改后的还是原来的？」

答：**改后的**。因为 `picked`（考生答案）是从**平台判分页的「考生答案」**
实时读的，而平台记的就是你实际提交的内容。

第 1 题原本 AI 答「对」，用户改成「错」，平台标准也是「错」→ 判对，33 分。
**如果没改，这题就错了，总分只有 67。**
