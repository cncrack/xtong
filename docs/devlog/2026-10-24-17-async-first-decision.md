# 会话记录 2026-10-24-17 — 并发模型决策翻转：M4 一步到位 async（方案 v0.13）

## 本次目标

用户质疑 v0.12 的"多进程优先"："本来就是考虑规模化的，为什么不一步到位？"——要求重新评估并登记。

## 结果

✅ 用户论点成立，决策翻转并登记为 v0.13：**M4 直接 asyncio + async Playwright，多进程降级为逃生舱**。

## 关键决策及理由

1. **推翻"多进程优先"的依据**：v0.12 的核心理由是"保护刚验收的同步代码"，但 M4 本就需要
   多账号实机验收——async 移植的行为复验与该验收是**同一批实跑，无额外成本**；此理由不成立。
2. **一步到位 async 的依据**：终态本就是 async（单机 Windows/Docker + FastAPI 异步面板 +
   几十账号目标）；sync→async 是机械移植（Playwright sync API 即 async 的生成包装），
   核心逻辑（额度/节奏/轮换/章节解析）纯 Python 零改动；绕道多进程 = 造注定废弃的中间层。
3. **落地要点（写入 §5.6）**：结构化并发（TaskGroup + supervisor 退避重启）；Semaphore 全局
   并发上限；错峰 = 账号任务按自身作息 await；单浏览器 + N 个 BrowserContext（context 级代理、
   按需惰性创建、UA/窗口微差）；FastAPI 面板同生态。
4. **多进程 = 逃生舱**：async 移植遇阻（如 Windows 事件循环兼容问题）时临时顶上，不作正式交付。
5. **移植纪律**：同步 StudyRunner 保留至 async 版通过同一套验收（整课实跑 + 测试全绿）后删除。
