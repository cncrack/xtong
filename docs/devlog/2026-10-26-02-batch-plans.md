## 三、关键决策及理由

### 3.1 批次表刻意**不含时间字段**

用户原话："账号能够统一起任务，但不能在同个时间点开始刷课，所以按原先定时器定时任务调度规则来进行跑。也可以单独对某个账号进行个性化设置。"

所以 `plans` 只有 `name / course_name / enabled`，**没有** `start_at`。
开跑时刻仍由 `auto` 守护原有的两处逻辑决定：

- 账号设了 `start_at` → 就用它（个性化设置优先）
- 没设 → `window_start + 随机 0~120 分钟`（天然错峰）

批次只回答"**这个账号今天该刷哪门课**"（`course_for_account()`），替代原本的课程轮转 `pick_courses()`。
这样"统一布置 + 各自错峰 + 单账号可个性化"三件事互不打架，也不用再造一个调度器。

### 3.2 一个账号只能在一个"启用中"的批次里

否则 `course_for_account()` 要面对两个答案。`create_plan()` / `set_enabled(True)` 都做冲突检查，
把冲突账号点名报出来（`#1（已在《十月》）`），让用户自己选停用还是剔除。
停用后的批次不参与判断，账号可随时改排到别的批次。

### 3.3 防多开的真实结构（回答用户第 1 问）

现在同账号单进程靠**两层**，批次与手动按钮共用：

| 层 | 位置 | 作用 |
|---|---|---|
| 进程内表 | 面板 `_JOBS[account_id]` | 面板自己拉起的会话，跨"手动/定时/批次"全都看得见 |
| 磁盘标记 | `data/run/<id>.json` + `pid_alive()` | 跨面板重启、跨 CLI（`xxt mlearn` / `xxt learn`）都看得见 |

`auto` 守护（批次真正生效的地方）**不自己 Popen**，而是 `POST http://127.0.0.1:8300/api/study/start`——
和用户点 ▶ 走的是同一个 HTTP 入口、同一段校验代码。所以：

- 手动先开 → 批次到点收到 `已有进行中的会话` → `fired.add(aid)`，今日不再触发
- 批次先开 → 用户点 ▶ 收到"该账号已有进行中的会话（定时/外部启动）"，不会起第二个 Chrome
- 批次内部也不会自撞：`fired/skipped` 集合保证每个账号每日只触发一次

**本次新增的补强**：`study_start` 里 `_spawn()` 之后立即 `write_marker(..., pid=proc.pid)`。
原因是面板拉起子进程后，子进程要走到 `xxt mlearn` 主流程才写标记，中间 1~2 秒面板只能靠内存 `_JOBS`；
如果有第二个入口（例如用户在命令行同时敲 `mlearn`）就会漏。现在出生即落盘，空窗归零。

### 3.4 批次在 UI 上的可见性

- 页面工具栏下方新增「📚 批次」区：一行一个批次（名称/课程/账号名单/启用状态 + 停用 + 删除）
- 账号卡片上多一行紫色小字：`📚 批次《X》→ 课程《Y》（开跑时间仍按本账号定时/窗口）`，
  避免用户以为"进了批次就会马上开刷"
- 新建弹窗里，已在其他启用批次的账号**置灰并标"已排"**，从源头防止冲突填写
