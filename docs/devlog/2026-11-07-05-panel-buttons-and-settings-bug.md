## 一、🔴 P0：面板设置的白名单漏了键 → 改了没效果，且**不报错**

### 现象（用户可复现）

「账号设置 → 面板设置」把**同时学习上限**改成 5 → 界面提示「已保存」→
但实际并发还是 2。

### 根因

`app.py::panel_settings_save` 里有一个**手写白名单**：

```python
items = {k: body.get(k) for k in ("reload", "poll_seconds") if k in body}
```

P2a/P2b 新加的 `max_concurrency` / `start_jitter` / `fleet_daily_minutes`
**没有加进这个白名单**。于是：

- 前端提交了 ✅
- `gxks_panel_settings.save()` 也支持 ✅
- 但在这一层被**悄悄过滤掉** ❌，而且**不报错**（过滤后剩下的 items 照样"保存成功"）

这与 2026-11-06 那个 `except sqlite3.Error: pass` 是**同一类骗人 bug**：
接口说成功、实际没生效，用户只能得出「改了没效果」，且没有任何线索。

### 诊断实证

```
POST {'max_concurrency': 5} → 回 ok:true
回包 settings 里 max_concurrency 仍是 2        ← 当场看到
```

### 修法

1. 白名单改成覆盖**全部可写键**，并加注释说明「必须与 `save()` 支持键一一对应」；
2. 回包新增 `saved_keys`（告诉前端这次到底哪些键被接受了，便于排查）；
3. **前端保存后用后端回包里的真实值回填控件** —— 原来只 toast 不刷控件，
   若后端钳制过（或白名单漏键），界面显示用户输入值、后端是另一个值，用户完全看不出；
4. 新增守卫测试 `test_whitelist_covers_every_default_key`：
   拿 `DEFAULTS` 的键集合与白名单集合做差集，**漏一个就红**。

### 修后实测（真实面板，端到端）

```
BEFORE: limit_concurrency=2 sections_per_run=3
SAVE  : ok=True saved_keys=['max_concurrency', 'sections_per_run']
AFTER : limit_concurrency=3 sections_per_run=5      ← 真的生效了
RESTORED: limit_concurrency=2 sections_per_run=3    ← 已还原
```

## 二、P1：两套勾选合并成一套（用户踩的那个坑）

### 原来为什么会有两套

2026-11-06 做卡片内批量时，刻意用了**独立的 `BATCH_SEL`**，理由是：

> 混用会导致「表格勾了 3 个准备删除，右侧栏突然也在批量里算 3 个」。

这个理由本身站得住，但**代价是使用者必然踩坑**：用户自然会在**表格**里勾 2 个账号，
然后去点右上角「启动并学习」→ 按钮是灰的（`BATCH_SEL` 还是空）。
用户原话：「我选几个账号，点击这个不就可以了吗」。

### 改成一份

- `batchBrowserAction()` 读 `[...SEL]`（表格勾选）；
- 卡片「全选」也改成填 `SEL`（等价于表头全选框），并顺手刷新表格上方的批量栏；
- 删掉 `BATCH_SEL` 集合。

### 用户问：这样对后期扩展和其它功能是否有影响？

已改的测试就是答案。影响面只有三个函数，且都是**只读 `SEL`**：

| 位置 | 影响 |
|---|---|
| `batchAction()`（表格上方批量栏） | 不受影响，本来就读 `SEL` |
| `batchBrowserAction()`（卡片批量） | 改读 `SEL` —— **这正是用户要的** |
| `batchSelectAll()`（卡片全选） | 改填 `SEL` |
| 表格行复选框 / 表头全选 | 不受影响 |
| 后端 `_stop_one` / `_study_one` / 批量接口 | **零改动**（都是按传入的 labels 干活） |

**扩展性上反而更好**：以后任何新批量动作只要读 `SEL` 就自动适用于"勾了哪些"，
不会再出现"这个按钮看 A 集合、那个按钮看 B 集合"。

⚠ 唯一要注意的是**语义变更**：现在「表格勾 3 个准备删除」时，卡片批量里也会算这 3 个。
但卡片批量只有三类动作（启动并学习 / 只启浏览器 / 停止），都是显式点击 + 二次确认，
不存在"误删"风险（删除只在表格批量栏）。

## 三、P2：表格批量栏加「启动并学习」

### 用户问：它和「启动浏览器」是否重复？

**不重复，是两个阶段**：

| 按钮 | 做什么 | 适合 |
|---|---|---|
| 「启动浏览器」 | 只拉起 Chrome + 注入登录态，**不进学习** | 想先确认登录状态 |
| 「启动并学习」 | 拉起 + 等端口就绪 + **直接开刷** | "我就是要它开始跑" |

后者 = 前者 + `_study_one`。后端 `start-and-study` **早就存在**
（`/api/accounts/batch` 已支持），缺的只是这个按钮 —— 所以用户勾了 2 个账号
却只能分两步点。

按钮顺序改成**从轻到重**：启动浏览器 → 启动并学习 → 开始学习（只在有账号
浏览器没开时出现前两个；都开着时「开始学习」就是主操作）。

## 四、P3：把「不能重复启动」说明白

原来浏览器已在跑时，按钮只是变灰，原因藏在 `title` 里（要悬停才看到）。
用户实拍：「启动并登录这个按钮还是高亮可点击的」。

现在**按钮文案随状态变**：

| 状态 | 文案 | 说明 |
|---|---|---|
| 端口活着 | **已运行**（灰） | title 写「端口 9223 已经在监听 = 浏览器开着，不需要再启动」 |
| 缺 Chrome | **缺 Chrome**（灰） | title 写怎么设 `XXT_GXKS_CHROME` |
| 其它 | 启动并登录 | 正常可点 |

后端本来就有闸（`_browser_start_one` 见端口活着就回 `skipped`），只是**界面没说出来**。

## 五、P4：修「已登录」撒谎

### 现象（用户截图里那两处）

```
端口 9233 未监听                                    ← 当前事实
上次检查 2026-11-06 20:57:16 · 已登录（导航了）      ← 昨天的事
```

于是界面一直绿着「已登录」，让人以为已经登好了。

### 根因

`renderBrowser` 的登录标签直接读 `session.logged_in`，**不看浏览器是否还活着**。
而 `session_<label>.json` 是**上一次检查的结果**，可能昨天写的；
浏览器关掉后 cookie 也早没了（本站 cookie 全是会话级）。

### 修法

- 判据改成 **`port_alive && session.logged_in`** 才是绿色「已登录」；
- 端口没开 → 「**未运行**」，title 写「浏览器没开，上次检查是 X 的结果，现在不适用」；
- 浏览器开着但没查过 → 「未检查」（原来是一片空白）；
- 「上次检查」那行追加「· 浏览器已关，此结果不适用」。

## 六、P5：`sections_per_run`（「本次跑几节」的默认值）

### 用户问：这个默认 3 和面板设置项是否同步？

**原来不同步**，而且「3」在**四个地方**各写死一份：

1. 表格行内输入框初值（`page.py` `Math.min(3, cap)`）
2. 批量 `start` 的 prompt 默认值（`"3"`）
3. `_study_one` 里 `int(max_sections or 3)`
4. 批量队列兜底 + `_start_and_study_one` 里 `or 3`

改一处其余不变，用户在面板设置里也**找不到这一项**。

### 现在统一

- 新增配置项 `sections_per_run`（1~12，默认 3，钳制与 `DEFAULTS` 同源）；
- `/api/state` 带下来，前端 `perRunDefault()` 统一读它；
- 表格行内初值、两个批量弹框的默认值、后端两处兜底**全部走它**；
- 「面板设置」新增控件「**每次跑几节**」，hint 写明与「账号日额度」的区别：
  - `daily_sections` = 这个账号**一天**最多几节（账号表属性，各账号可不同）
  - `sections_per_run` = 点一次「学习」**这一次**最多跑几节（全局默认，行内可临时改）
  - 两者取小（11-04 定下的口径），所以调大不会超刷。
