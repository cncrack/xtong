## 二、上午最有价值的三个发现

### 1. 「选了 2 个账号只启动一个」的真因是**点错按钮**

不是并行代码的问题。右侧小面板「启动并登录」是**单账号**按钮
（`browserLabel()` = `HOVER_LABEL || LABEL`，永远只指一个），左侧表格上方
「启动浏览器」才是批量的。

**决定性证据**（上午加的批量留痕起了作用）：

```
11:07:21 | (批量) | batch | ok | 批量「start-browser」提交 2 个：成功 1（default）、
                                  跳过 1。原因：test=端口 9233 已在运行
```

**教训**：多账号问题先确认「动作从哪个入口发的」，比读代码快得多。

### 2. 「端口活着 ≠ 登录态有效」

`.ASPXAUTH` 是**会话级** cookie（`expires=-1`）：关窗即失效，服务端也有超时。
旧逻辑一看端口在监听就 `skipped`，**连登录态都不看** —— 于是浏览器开着却停在
`Loginb.aspx`。

CDP 实证：

```
9222 → 考试平台        | MainPage.aspx  （已登录）
9233 → 考试平台--登录  | Loginb.aspx    （被踢）
```

方案 A：端口活着时**只读**查一次登录态；已登录→跳过，掉登录→就地补登录，
探不出来→保守跳过。

### 3. 操作记录里的 `ops` 查询把批量记录整条滤掉了

```python
ops = gxks_ops.recent_ops(db, account_label=label or None, limit=60)
```

批量动作写的是 `account_label=""`，这个过滤会把它**整条滤掉** —— 用户看不到批量记录。
这也是上午排查慢的原因之一。
