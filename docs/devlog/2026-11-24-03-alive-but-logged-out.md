## 一、查清的事实

### 两个账号的快照与现状

| 账号 | 快照时间 | cookies | CDP 实际页面 | 结论 |
|---|---|---|---|---|
| `default` | **11:07:21**（刚登录） | 8 个 | `MainPage.aspx` | ✅ 已登录 |
| `test` | **09:15:04**（近 2 小时前） | 6 个 | **`Loginb.aspx`** | ❌ 被踢回登录页 |

用 CDP `/json/list` 直接读页面标题，这是**不可伪造的判据**：

```
port 9222 → 考试平台        | MainPage.aspx?menu=3&subMenu=4
port 9233 → 考试平台--登录  | Loginb.aspx
```

### 为什么「有 cookie」却登不上

`.ASPXAUTH` 的 `expires = -1` → **会话级 cookie**：

1. **浏览器关掉就没了**（所以必须存快照再注入）
2. **服务端的 Session 有自己的超时**（ASP.NET 默认 20~30 分钟）

test 的快照是 09:15 存的，到 11:07 已隔近 2 小时 → 服务器早清了这个会话 →
注入进去的 `.ASPXAUTH` 是**服务器不认的旧票据** → 平台直接跳 `Loginb.aspx`。

**这不是 bug，是 ASP.NET 表单认证的固有行为。**

## 二、真正的代码缺陷

操作记录已经写得很清楚（11-24 上午刚加的批量留痕，这次直接派上用场）：

```
11:07:21 | (批量) | batch | ok | 批量「start-browser」提交 2 个：成功 1（default）、
                                  跳过 1。原因：test=端口 9233 已在运行
```

**「跳过」= 什么都不做。**

旧代码：

```python
if state["port_alive"]:
    return {"ok": False, "skipped": True, "message": f"端口 {acc.port} 已在运行"}
```

它**连登录态都不看**。于是：

- 用户点「启动 2 个」→ 期望两个都可用
- 实际：一个被启动并登录，另一个因为「窗口开着」被跳过
- 那个窗口停在登录页 → 用户以为「有 cookie 怎么登不上」

**根因一句话：把「进程活着」当成了「可以用了」。**

## 三、方案 A（用户拍板）

端口活着时**顺手查一次登录态**，分三种结果：

| 探测结果 | 动作 | 返回 |
|---|---|---|
| **已登录** | 什么都不做 | `skipped`（附「且已登录」） |
| **掉登录** | `_chrome_start_message` → 注入快照 / 密码重登 | **`ok: True`**（用户要的状态达成了） |
| **探不出来**（脚本异常） | 什么都不做 | `skipped`（保守：不冒险动用户的浏览器） |

### 关键设计：探测必须是**只读**的

```python
def _session_probe(acc, run_session):
    out = run_session(acc)          # 不带 --restore / --relogin
    ...
```

**为什么不直接调 `_chrome_start_message`**：那个函数会**动手**（注入 / 重登）。
对一个可能正在正常工作的浏览器，必须先确认「真的掉登录了」再动手 ——
否则每次批量点一下就把用户的会话重置一遍，还可能触发验证码。

**测试专门守这一点**（`test_probe_is_read_only`）：
断言 `_session_probe` 里不许出现 `--restore` / `--relogin` / `_trigger_chrome`。

### 文案区分

```python
msg = (f"Chrome 已在运行（端口 {port}）" if already_alive
       else f"Chrome 已启动（端口 {port}）")
```

补登录时不能说「已启动」，否则用户以为窗口是刚开的、白等一轮。

## 四、代价与风险

| 项 | 说明 |
|---|---|
| **多一次平台访问** | 每个「端口已活」的账号探一次（本地 CDP + 一次页面 GET）。7 个账号批量 ≈ 7 次 |
| **可能触发验证码** | 掉登录时会尝试密码重登；平台要求验证码 → 转人工（原有三层策略不变） |
| **探测失败不会误伤** | 返回 `None` 时保守跳过，不重登 |

⚠ **仍需注意**：如果多个账号同时掉登录又都配了密码，批量会**同时**尝试重登。
这在风控上不是最优雅的形态。若真遇到，可以后续加「重登串行 + 间隔」。
