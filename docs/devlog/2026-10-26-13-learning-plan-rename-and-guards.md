# 会话 41：「批次」改名「学习安排」+ CLI 双开守卫 + 缺课保护

日期：2026-10-26（承接会话 40 的「定时任务为何没启动」，本会话回答"批次优先是什么意思"）

## 一、用户问题（原话）

> 这个是什么意思，批次优先的话，如果我没有建批次呢，如果我启动了某个账号，而这个账号又在批次中，会不会有双开的情况？
> 要先批次才能刷课这点不合理吧，这个是什么意思，解释清楚，是否有更加妥当的描述名称？可以测试一下

拆成四问：① 没建批次能不能刷课 ② 账号在批次里 + 手动启动会不会双开 ③ "批次优先"到底是什么 ④ 名称是否不妥。

## 二、结论（先给答案，后附证据）

| 问 | 结论 |
|---|---|
| ① 没批次能刷吗 | **能**。启发式：启用中的学习安排指定课 → 否则课程轮转（优先级×未完成度加权随机）→ 都没有才跳过。"批次优先"只是"有就用它"，**不是前置条件** |
| ② 会双开吗 | **面板/定时侧不会**：两者共走 `POST /api/study/start`，同一把锁（进程内 `_JOBS` + `data/run/<id>.json` 标记） |
| ②补充 | **CLI 侧曾有真漏洞**：`cmd_learn` 有 `live_session` 守卫，`cmd_mlearn` 只 `write_marker` 不检查 → 面板在跑时再敲 `xxt mlearn` 就是双开。本会话补齐 |
| ③ 语义 | "同批任务"共享**课程**，**不共享时刻**；开跑时间仍按各账号 `start_at`/窗口错峰（`plans` 表无时间字段） |
| ④ 名称 | 用户拍板改为「**学习安排**」——它是长期配置（哪门课排给哪些账号），不是"一次性批量操作"；旧名容易被读成"必须建了才能干活" |

## 三、关键决策

1. **改名不改语义**：`plans` 表、API、`core/plans.py` 结构一律不动，只改展示名与文案；顺带把 tab/弹窗/空状态写清"可选功能…不建也能刷"。
2. **双开守卫放在 CLI 入口**而不是 `run_accounts` 内部：面板已有一把锁，CLI 只需"启动前问一句"，避免两套锁逻辑漂移。`--force` 留给明确知道后果的并行场景。
3. **缺课保护做在服务端**（`/api/study/start`）+ 守护侧本地预核：问题不是"跑不起来"（子进程会 `[FAIL]` 退出），而是**调用方拿到 `ok=True` 后记为"今日已触发"，当日机会白白消耗**。两处都用 `plans.account_has_course`（纯本地查库，零平台访问）。
4. **诊断脚本零平台访问**：双开/缺课两个实测都靠伪造 `data/run/<id>.json` + 不存在的课程ID，没有碰学习通。

## 六、踩到的环境坑（重要）

**`.venv\Scripts\xxt.exe` 跑的是旧项目代码**。`.venv` 是从 `E:\code\xxt\.venv` 拷来的，`pyvenv.cfg` 里 `command = … E:\code\xxt\.venv`，控制台启动器 shim 内嵌的 python 路径也还指向 `E:\code\xxt\.venv\Scripts\python.exe` → 那个 venv 的 `.pth` 指 `E:\code\xxt\src`（旧代码，面板页 39901 字符、连 `plans` 功能都没有）。

发现方式：实测"缺课启动"返回 `{"ok": true}`（新代码必然拒绝）→ 怀疑跑的是旧代码 → 比对页面长度（旧 39901 / 新 77288）与 `/api/plans` 是否 404 → 查进程链得证。

修复：`.venv\Scripts\python.exe -m pip install -e . --no-deps`（不带 `--no-build-isolation`，否则 venv 缺 `bdist_wheel` 会失败）。修完 shim 内嵌 `E:\xxt\.venv\Scripts\python.exe`、`.pth` → `E:\xxt\src`，经 `xxt.exe panel` 启动的页面已是 77288 字符（新代码）。

**给后续会话的教训**：面板改完代码重启后，先 `GET /` 比一下字符数或关键文案，别默认"重启就生效"。

## 七、追加：实测定时守护的决策链（用户担心“随便刷”）

用户追问：“定时守护刷是怎么自动轮转挑一门？如果学生没有要学那门你随便刷，那不是出事了？守护管学习安排还是也管每个账号？”

### 干跑（`data/debug/diag_auto_dry.py`，纯本地库）

```
#1 default：权重 0.600 《知行合一，做最好的自己》→ 抽 8 次均为它
#2 小号1 ：权重 0.686 《知行合一，做最好的自己》→ 抽 8 次均为它
守护决策链：#1 计划 10:14 / #2 计划 09:20｜来源=课程轮转｜抓到过=True｜已登录=True
```

权重公式（`core/rotation.py::course_weights`）= `优先级(默认 1.0) × 未完成章节 / 总章节`；
`pending==0`（已学完）与无章节课直接出局。**多门时会随机，但并非无偏好**；
本次两号都只有一门候选，所以看起来“固定”。

### 真起守护（`data/debug/diag_auto_live.py`，把计划时刻临时推到 23:50/23:55）

```
POST /api/auto/start → {"ok": true}；auto = {"running": true, "since": "11:39"}；jobs = {}
子进程日志：
  [auto] 守护启动。到点后经面板启动学习会话（面板可见、可 ■ 停止）
  [auto] 账号#1 default 今日计划 23:50 开刷
  [auto] 账号#2 小号1 今日计划 23:55 开刷
app_config['auto.plan'] = {"date":"2026-10-26","times":{"1":"23:50","2":"23:55"}}
POST /api/auto/stop → {"ok": true}；start_at 已还原 {1: '10:14', 2: '09:20'}
```

结论：守护**逐账号**巡检（active + 在有效期内），每号用自己的 `start_at`（空则窗口起 +0~120min 随机）；
到点前只记计划不开刷（本次零平台访问)；学习安排只决定“刷哪门”，不决定“什么时候刷”。

### 顺带修：子进程 print 被缓冲吞掉

首次实测日志**只剩一行**“守护启动”（logging 那条），“今日计划 xx:xx 开刷”全不见——
因为 `_spawn` 没加 `-u`，进程被 terminate 时缓冲区丢掉。已改：`argv` 加 `-u` + env 加
`PYTHONUNBUFFERED=1`（exe 模式靠 env 生效），重启面板复测日志如上。

### 已知风险（待用户决定，未改代码）

1. **守护不校验 `window_end`**：算计划时刻只用 `window_start`；若 `start_at` 落在学习窗口外，
   子进程会立刻以“超出每日学习时段”退出，而面板已回 `ok=True` → 当日机会白耗（同缺课问题同类）。
2. **多门课时轮转=随机**：不建学习安排就会随机挑；要指定就必须建学习安排并启用。
3. `start_at` 已过时，一启动守护就会对全部账号立刻补跑（两号会同时开）。

### 另一处踩坑：诊断脚本名叫 `test_*.py` 会把 push_check 弄挂

`scripts/push_check.py` 跑的是裸 `pytest -q`，而 `pyproject.toml` 当时没有 `testpaths` →
递归收集到 `data/debug/test_*.py`（现场诊断脚本，import 时就要访问面板/平台）→
`3 errors during collection` → 门禁 FAIL，而手动 `pytest -q` 又“看起来正常”。
修：① 诊断脚本统一改 `diag_*.py`；② `pyproject.toml` 加 `[tool.pytest.ini_options] testpaths = ["tests"]`，
以后只在 `tests/` 收集。
