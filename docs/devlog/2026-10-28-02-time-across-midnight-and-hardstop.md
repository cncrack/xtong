## 三、关键决策

1. **A 用「环形分钟比较」而不是改库存绝对时间戳**

   - 放 `core/pace.py`（纯逻辑、无 playwright），`cli` 与面板共用一个判据——以前 `cli.py:1350` 与 `app.py` 各自写字符串比较，同一个坑两个地方。
   - 为什么 12 小时够：退避封顶 `retry_max_minutes` = 480 分钟（8 小时）< 720。
   - 放弃“把 `auto.retry_after` 的值改成 epoch”：要改 JSON 结构 + 兼容老值，且面板展示仍要 `HH:MM`；环形比较零迁移就正确。
   - 到点即跑：`gap == 0` 返回 False（与旧语义 `now < target` 一致），否则“正好到点”会多等一轮。
2. **A 同时修面板的 `resume_at` 过期判断**：原来 `resume_at <= now_hm` 会把 23:50 时的 `00:20` 误清成空，卡片上“约 00:20 自动重试”消失。
3. **B 新增事件 `auto-hardstop`，不回看文案**
   - 三处硬停（`_revive_if_dead` 用尽、回读分支的 `window` 与“退避都用尽”）全部改写 `auto-hardstop`。
   - `_replay_auto_events` 里与 `auto-done` 合并为“今日已收工”，重启后 `fired` 恢复、不再撞。
   - 为什么不做“`auto-error` 一律当失败”：`auto-error` 还表示“面板没响应/触发失败”（`cli.py:1455`，30 秒后重试），一律当失败会让它在重启后被永久锁死。
   - 为什么不用“文案里含硬停”判断：正是 Q30 的老毛病（自己产的事件还要靠中文猜）。
4. **面板保留旧行兼容**：`auto-error` + 文案含「硬停」仍标硬停（历史数据不改），新行走 `auto-hardstop`。

## 五、关于「为什么要先重启守护」（用户明确问）

两件事不要混：

1. **改账号定时 → 不需要停守护。** 守护每轮会比对 `row["start_at"]` 与缓存计划，运行中改会写 `auto-replan｜#N 定时改为 HH:MM（原 …）` 并立即按新时刻执行（`cli.py` 计划同步块）。
2. **改代码 → 必须重启守护与面板。** Python 进程不会热加载，不重启跑的还是旧逻辑。本次 A/B 正好在守护的每轮巡检里，所以**明早动手前重启一次**才能看到新行为。

重启**不会**带来副作用，这点已核实：`tries`/`suspend_n`/`fired` 都从 `run_logs` 回放；手动停的号靠库里的 `session-stop` 让位（Q29），重启也起不来；退避表从 `app_config` 恢复，且现在跨零点也能正确恢复。

正确顺序：停面板 + 守护 → 起面板 → 起守护（▶ 自动）→ 再改定时。
