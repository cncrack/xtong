## 一、🔴 真实缺口（会造成错误，不是"不完美"）

### A1. 同账号可能被双开 —— 面板的并发闸只防了"面板自己"，没防"别的入口"

| 项 | 内容 |
|---|---|
| **事实** | ① `scripts/run_gxks.py` 里**零处**引用 `runmark`（`grep runmark` = 0）；② 面板 `_study_one()` 防双开只靠**内存表** `_JOBS`（`if any(j["label"] == acc.label ...)`）；③ 面板 spawn 子进程时**没传任何锁参数** |
| **后果** | 同时存在两个入口就能双开：**面板 A + 面板 B**（`E:\xxt` 那个 worktree 也抢 8301，只需换个端口）、**面板 + 手敲 `run_gxks.py`**、**面板重启后旧任务还没死 + 又点一次**（靠 `adopt_orphan_jobs` 认领才有救，认领失败就漏）。同账号两路心跳是**最强的机器指纹**，也正是 PLAN §对策⑦ 明确禁止的 |
| **对比** | 超星侧早就做了账号级会话锁（`core/runmark.py` + `data/run/<id>.json`），gxks 侧**一直没接**。`runmark` 是共享模块，接线成本不高 |
| **建议方案** | 在 `run_gxks.py` 启动处写标记（复用 `runmark.write_marker`，`account_id` 用 label 的稳定哈希或账号表序号），收尾 `clear_marker`；`busy_sessions` 判到「别的活进程持有」就 `[FAIL]` 秒退。面板 `_study_one` 先查标记再 spawn。**注意 `runmark.py` 注释里已记过的坑**：venv 的 `python.exe` 是重定向器，`Popen` 拿到的 pid ≠ 真 pid，判据要用 `pid ∈ {me, parent}` |
| **验收** | ① 面板点学习 → 手动再跑 `run_gxks.py --label 同一号` → 必须秒退并说明原因；② 连点两次「学习」→ 只起一个；③ 任务自然结束后标记被清（再跑能起） |
| **优先级** | 🔴 **最高** —— 这是封号红线，且 `PLAN-GXKS.md:222` 早就把它列为"三条硬约束"第 1 条（"账号级会话锁：一账号一进程一会话（沿用 core/runmark 的思路）"），**一直没落地** |

### A2. 两套并发口径打架：面板默认 2，`run_gxks_multi.py` 硬性"并发 1"

| 项 | 内容 |
|---|---|
| **事实** | `scripts/run_gxks_multi.py` 开头写着「为什么是**串行**（并发 1）：PLAN-GXKS D12 —— 同一出口 IP 上多账号同时刷，是最容易被风控关联的特征」；而 11-06 新加的面板并发闸**默认 2** |
| **后果** | 两条路给出相反的答案：用户从面板起 = 2 个并发（D12 说违规），从 multi 脚本起 = 1 个（符合 D12）；而 `PLAN-GXKS.md:509` 的配置草案又写 `max_concurrency = 10`（用户 2026-10-29 暂定）。**三个数字：1 / 2 / 10，没有一个权威来源** |
| **建议方案** | 在 PLAN 里**明确 D12 的适用范围**：是"核实期临时约束"还是"长期风控约束"。若长期 → 把 `run_gxks_multi.py` 也改成可配并发（而不是硬写串行）+ 面板默认跟随；若只是核实期 → 在 PLAN 记「核实期结束、产品并发已确认 = N」，并把三处统一到 N |
| **优先级** | 🔴 高 —— 不是代码 bug，是**决策空缺**，会持续产出矛盾文档 |
