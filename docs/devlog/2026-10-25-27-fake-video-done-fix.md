**铁证**：两条 `video-done` 相隔 8 秒，时长完全相同（494s）——后一条"下"其实是前一条"上"的时长。

| id | 时间 | 详情 |
|---|---|---|
| 158 | 22:49:53 | 正确认识自我（上）｜494s（真） |
| 159 | 22:50:01 | 正确认识自我（下）｜494s（假，已删） |

机制：`watcher.js` 每 3 秒发一次 `tick`（`setInterval`，见文件第 30-38 行）。点"下一节"后
旧文档还在跑，拟人间隔的 8 秒里持续往 `__xxtEvent` 写事件；新一轮 `_play_video` 一
`_drain()` 就把"上一节 `cur=495/dur=495`"当成了新视频的状态 → 立刻判"播完" →
写假 `video-done` + 章节误标 `done` → 紧接着页面真正开始换视频、播放器重建，
`watcher` 注入失败、再点"下一节"点不到 → 代码判"确已到末尾" → 会话结束。

## 三、三处修复

1. **注入前后清队列**（`astudy.py` / `study.py` 的 `_play_video`）：这是根因级修复。
   `self._drain()` 在注入前清一次、注入后再清一次，残留事件不再进入新视频的判定。
2. **"完成"必须可信**（新增 `core/playback.py::is_plausible_completion`）：只有
   ① 见过 `cur < dur-5` 的真实进度，或 ② 实际耗时 ≥ `min(时长/倍速 × 0.5, 20s)`，
   才认"播完"。都不满足 → 继续观察；连续 5 个 tick（约 15 秒）始终停在末尾 →
   判为"平台侧本来就已完成"，**只标章节、不写 video-done**（额度不虚增、也不会死循环）。
   `_play_video` 因此由 `bool` 改为三态：`True`=真播完可记账 / `"already"`=平台已完成 / `False`=没播成。
3. **"到末尾"改查本地章节表**：`下一节` 点不到时先数 `chapters.status='pending'`——
   还有就报"页面未就绪，本地仍有 N 节待学"，为 0 才报"全部章节已学完"。
   **按钮状态不可信，数据库才是真相。**

## 四、回应"要不要删同步版"

这次崩溃**不是** sync/async 混用，是同一个引擎里的状态误判——所以删同步版解决不了这一类。
两者是独立的两件事：

| 问题 | 删同步版能否解决 |
|---|---|
| sync/async 混用（10-25 两次：`hardened_context`、`username_sniffer`） | ✅ 能（消除诱因） |
| 播放器状态误判 / 假 video-done / 误报到末尾 | ❌ 不能（两个引擎都要单独修，本次已双修） |

而且删同步版**没有想象中简单**：`study.py` 里的同步 page 工具仍被作业链路使用——
`cli.py:590`（`cmd_work`）与 `panel/app.py:1402/1582`（参考答案、判分回读）都是
`from .adapters.chaoxing.study import find_frame_with, open_chapter_frame`。
真正的做法是：把这些同步工具挪到 `chaoxing/pageutils.py`（明确标注 sync-only），
再删 `StudyRunner`（约 295 行），并把 `cmd_learn` 改走 `run_accounts`。约 1.5 小时。
建议：**等实跑稳定后再做**（现在最重要的是验证今晚这批修复）。

## 七、教训

**进程内的状态机里，"上一轮的事件"比"这一轮的页面"来得更快。** 凡是跨任务点/跨视频
复用的队列、缓存、frame 引用，切换时必须显式失效；判定"完成/到末尾"这类**有后果的结论**，
必须锚定在一个比界面更可靠的真相源上（这里是 `chapters` 表、`video-done` 记录）。
