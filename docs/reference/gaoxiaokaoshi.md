## 二、平台结构情报（摘自上游实现，全部待实测核对）

### 2.1 页面类型与路由

脚本靠 URL 片段分派（我们写 adapter 时**别照抄它的硬拼法**，见 §四·红线 3）：

| 页面类型 | URL 片段 | 用途 |
|---|---|---|
| login | `loginb.aspx`（真实入口）；脚本判的是 `login.aspx` | 登录 |
| courseList | `librarystudylist` | 课程列表 |
| main | `mainpage` | 主框架（含 `#mainIframe`） |
| exam | `examtmstepdo`、`examdo.aspx` | 答题页 |
| examHeader | `examtmstepheader` | 交卷（顶部框架） |
| examMessage | `exammessage` | 交卷成功 |
| examView | `viewexam` | 查看答卷（收录正确答案） |

### 2.2 关键 DOM / 控件

| 用途 | 选择器 |
|---|---|
| 主框架 iframe | `#mainIframe` |
| 视频所在 iframe | **`#ExamView`**（内部 `document.querySelector('video')`）→ 与我们超星的 `pagesync.find_frame_with` **同构** |
| 播放器容器 | **`#J_prismPlayer`**（需 `player.click()` 才真播，防浏览器自动播放策略） |
| 课程行 | 纯 `tr` 六列：课程名 / 类型 / 总时长 / 已学时长 / 状态（文本 `已完成`）/ 学习按钮 |
| 分页按钮 | `#PageSplit1_BtnNext`（WebForms postback） |
| 页码文本 | `.page .fright ul li`，形如 `2/5` |
| **服务器同步时间** | **`#spTitle`** |
| 题目 | `.exam_list dt`（兜底 `.tb_content dt`） |
| 选项 | `input[id^="tm_{题号}_{字母序号}"]`，选项文字在对应 `label`（取其内容去掉前 2 字符） |
| 答卷页每题容器 | `div[id^="ddTm_"]`，**正确答案用 `.green` 类标色** |
| 交卷 | 调 `window.SubmitExam()`，兜底点 `a[href*="SubmitExam"]` |
| 看卷按钮 | `#btnView` |

### 2.3 计时与续播机制（最重要的一条）

- `#spTitle` 显示**服务器同步时间**；上游脚本每 60 秒读它，**两次内容相同就判定"数据同步异常"→ 刷新页面**。
- 含义：**服务端按自己的时钟累计学习时长**，与客户端 `video.currentTime` 推进多少无关 →
  **倍速播放无效**（上游 README 也明写"观看进度按实际时间计算，无法倍速"）。
- 续播：从课程表的「已学 X 分钟」解析出分钟数，直接 `video.currentTime = X * 60` 跳到未看部分。
- 视频事件：`onended` → 刷新继续下一个；`onpause` → 1 秒后重试 `play()`；`onerror` → 刷新；加载检查计数器到 8 次仍无视频 → 刷新。

### 2.4 题库机制（与我们的 AI 作答对照）

- 题库存浏览器 `localStorage`，key 为 `题库`，结构 `{ 题干文本: [答案文字...] }`。
- 题干由正则 `/\d+\.(.*)\(/` 从题目 `dt` 文本截取（**只取到左括号前**）。
- 答题页：命中题库则按选项文字匹配并 `click()`；未命中跳过。
- 交卷后自动进 `viewexam`，读 `.green` 标色内容回收正确答案入库（判断题会把 `对/正确`、`错/错误` 都写进答案数组，选择题按 A~H 字母反查选项文字）→ **多考几轮题库自然变全**。
- 跨 iframe 协作：答题页写 `localStorage.examAction = done:<时间戳>`，交卷框架 5 秒内看到该标记才交卷。

## 三、与超星的关键差异（决定哪些参数不能照抄）

| 维度 | 超星（现状） | 高校考试网（待实测） | 影响 |
|---|---|---|---|
| 倍速 | `speed_range=[1.0,1.25]` | **无效**（服务端按自己时钟计） | 新站 `pace.speed` 失效；耗时/额度估算不能按倍速折算 |
| 并发 | **严禁多端并发**（防封地基，单账号单进程） | 上游称"没有观看检测，可多开"，但 README 建议 **≤5 页** | 有提速空间，但属风控未验证区，**首版不建议多开** |
| 登录 | https + 人工辅助登录存会话 | **明文 http**（443 不通）+ 真实入口 `Loginb.aspx` | 凭据与 cookie 明文过网络 → 见 §四安全约束 |
| 题目反爬 | 动态字体混淆（`font_cipher.py` 109 行） | 上游实现未见任何字体处理 | **`font_cipher` 大概率不用带过去** |
| 自愈 | B3「重载任务页续播一次」+ 四档状态机 | 全靠 `location.reload()` | 新站照搬我们的状态机，不照搬它 |

## 四、开工时必守的约束与红线

**安全（因该站是明文 http）**

1. 凭据只走 `core/crypto.py`（AES-256-GCM）落盘，绝不进 `settings.toml` / 代码 / 文档。
2. 日志与事件**不打印任何凭据与 cookie**（`scripts/push_check.py` 敏感扫描覆盖此项）。
3. **不在公共网络 / 不明 WiFi 登录该站账号**（超星至少是 https，这条要求更严）。

**实现红线（上游能跑 ≠ 我们对）**

1. **绝不全局劫持 `window.confirm/alert`**。上游用 `Object.defineProperty(..., {writable:false, configurable:false})` 让 `confirm` 恒返回 true 来"不被弹窗卡住"——若平台用 confirm 确认"确实交卷？"就是**误交卷**。我们处理弹窗必须显式 accept/dismiss **并写事件记账**。
2. **自愈不得退化成 `location.reload()` 循环**（会丢定时器状态）。用我们已有的 `runmark` + 事件记账 + 四档状态机（Q19）。
3. **登录页匹配用正则包含式** `login\w*\.aspx`，不要硬拼文件名 —— 上游用 `pathname.indexOf('login.aspx')`，**匹配不上真实入口 `loginb.aspx`**（照抄别人的匹配值就是坑）。
4. **题库 key 用 `question_hash`（sha256(题干+选项)），不用题干原文** —— 上游 `bank[题干]` + 截断正则，题干标点/空格一变就 miss。
5. **必带低频拟人化**：`pace` 三档间隔 + `daily_max_minutes` 额度 + 每日窗口。上游是零间隔、零额度、零并发控制（`onpause` 后 1 秒立即 `play()`、`volume=0`、全天可跑），这恰好是风控最典型的机器人形态。
6. 平台细节只写在 `src/xxt/adapters/gaoxiaokaoshi/` 内（AGENTS 硬性约定）；开工前先把 **Q27**（超星用词漏进 `core/diagnose.py`）还清，否则新站会照着错误示范写。

## 七、特征检测与封号风险（2026-10-27 21:05，**A 级实测**）

### 7.0 本次做了什么（合规声明）
只 GET **公开页**（`/`、`Loginb.aspx`、`MainPage.aspx`）与它引用的 3 个 JS；**无凭据、不填表、不提交、不登录**；每 URL ≤4 次尝试带随机间隔，共约 10 个请求。探针：`data/debug/probe_gxks_{loginb,headers,pages,js}.py`（不入库），产物 `data/debug/gxks_html/`。

### 7.1 结论：**客户端零检测，风控全在服务端**

| 检测面 | 命中 | 判读 |
|---|---|---|
| 自动化检测（`webdriver`/`phantom`/`selenium`/`headless`/`$cdc_`）| **无**（三页 HTML + `Login.js` 6555 字符 + `index.js` 1852 + `Dialog.js` 27830 全扫零命中）| 站方不做浏览器端机器人探测 |
| 指纹采集（canvas/webgl/plugins/toDataURL）| **无** | 同上 |
| 埋点上报（beacon/cnzz/umeng/gtag）| **无** | 无第三方分析代码，也就没有“上报环境”的通道 |
| `navigator.userAgent` | 仅 `Dialog.js` 判 `isIE/isIE6/isGecko` | **2010 年代的浏览器兼容分支，不是风控**；用正常 Chrome UA 就走“非 IE”分支，与人一致 |
| `window.onerror = function(){return true;}` | loginb 内联 | 吞 JS 错误（老站常见），不是检测 |

**由此的风险定性**：被封不会因为“被识别为脚本”，只会因为“行为异常”与服务端判定。

### 7.2 服务端暴露的两处风控痕迹 ⭐ 本次最重要的发现

1. **`Loginb.aspx?needVerify=1` = 可升级的验证码闸门**
   页面上是 `<tr id="trVerify" style="display:none">`，末尾脚本 `if(location.search.indexOf('needVerify=1')>-1)` 才把它显示出来；验证码图 = **`VerifyCode.ashx`**（服务端生成 4 位，`maxlength=4`，点击刷新 `?t=Math.random()`）。
   → **正常登录不要求验证码；站方判定可疑才会带你到带 `needVerify=1` 的页面**。这是**封号前的最后一道闸门**，也是我们能感知“已被判可疑”的唯一可见信号。
   → **设计定论**：adapter 必须识别 URL 上的 `needVerify=1` 并**立即停止自动登录、转人工**，绝不自动试错验证码（连续试错 = 撞库特征，最危险）。
2. **密码明文 POST、无客户端哈希**
   `CkeckNotNull()` 仅做非空校验，然后 `document.getElementById("frmLogin").submit()`；字段 = `name` / `pw` / `verifyCode` / `screenType`（hidden，值 `1440` 为服务端渲染）；表单 `action="HidLogin.aspx" method="post"`。
   → 没有任何“客户端加密指纹”需要复刻（好事：实现简单；坏事：明 http 下凭据完全裸奔，见 §四）。

### 7.3 站点稳定性：间歇 503（**推翻我 20:10 的判断**）

实测：root 第 1 次 503；loginb 第 1 次 **`RemoteProtocolError`（收到 1139/2785 字节被对端截断）**、第 2 次 503、第 3 次 200；mainpage 直接 200。**同一 URL 换 UA 结果相反**（`/` 空 UA 时 503、`Loginb` 空 UA 反而 200）→ 是随机而非按 UA 判定；响应为**空 body、无拦截页、无 `Retry-After`、无 WAF 头**（`Server: Microsoft-IIS/10.0` + `X-ASPNET-Version: 4.0.30319`）。

🔴 **自纠**：20:10 我根据“两次抓取为空 body”断言“服务器对非浏览器不给内容 → `httpx` 直取不成立，必须真 Playwright”——**错了**，那是撞上间歇 503。真相：`httpx` 带正常 UA **能稳定取到公开页 HTML**（配合重试）。
→ 影响：新站的**课程列表/登录**可走轻量 HTTP（更稳、足迹更小），**只有播放器计时与 iframe 交互需要真浏览器**；开工时按这个分层重估一遍工作量（但 §0.2 定的人天不立刻下调，因为登录后的页面仍未实测）。
→ 另一头提醒：**503 不是拦截，不要把它当风控信号去“绕过”**；重试要上限 + 退避（疯狂重试反而可能把自己送进 `needVerify`）。

### 7.4 登录形态（原 A2/A3 假设已答）

- **账号 + 密码 + 可选图形验证码**；**无手机号/短信验证码**（页面文本只有「账 号 / 密 码 / 验证码 / 忘记密码？」，无“手机”“学籍”“身份证”字样）
- `Login.js` 函数表里有 `isEmail` / `chkExitsEmail` / `check_username` / `chkRegInfo` / `frmReg` → **账号可能是邮箱且平台支持自助注册**（待有账号后确认，与风控无关）
- `Loginb` 的 `b` 与处理页 `HidLogin.aspx` 的关系待后期看，不影响策略

### 7.5 防封对策（新站首版默认执行，宁保守）

| # | 对策 | 理由 |
|---|---|---|
| 1 | **首版不开多开**（上游说“可多开 ≤5 页”也不接）| 单账号并发是行为异常首要特征；我们的优势在多账号调度不在单号并发 |
| 2 | `pace` 三档间隔 + `daily_max_minutes` + 每日窗口全带，**新站额度从超星的 50~70% 起步** | 服务端按自己的时钟计时，“一天刷满 10 小时”直接写在它的库里 |
| 3 | **撞 `needVerify=1` 即停并转人工**，禁止自动试错验证码 | 这是站方给的唯一“已被判可疑”信号，硬撞最容易升级为封号 |
| 4 | 单账号单进程单会话（沿用超星地基）；会话失效走 `relogin` 且**每日登录次数有预算** | 多端并发/频繁重登是最典型机器人特征 |
| 5 | 503/截断按“服务不稳”处理：上限 3 次 + 指数退避 + 随机抖动（复用 `retry_jitter_pct`/`retry_max_minutes`）| 避免重试本身成为异常行为 |
| 6 | 只在**自有网络**登录；凭据走 `core/crypto`；日志零凭据零 cookie | 平台侧不加密，我们侧必须补 |
| 7 | **不逆向 `HidLogin.aspx` 直接 POST 登录**（即使技术上可行）| 绕开正常流程是最强机器人特征，且明 http 下凭据更暴露 |

### 7.6 本次探不到的（诚实边界）

服务端的**判定规则看不见**：是什么触发 `needVerify`（IP 频次？账号异常时长？并发登录？错密次数？）——只有真实账号小规模跑才能校准。**开工后第一批实测项就查这个**：看一个正常人工登录账号在什么行为后开始被要求验证码（对比线索法，与超星 Q19 同思路）。
