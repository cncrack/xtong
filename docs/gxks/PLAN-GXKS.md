### 1.3 题库与答题方案（用户 2026-10-27 深夜追问，已答）

用户问：“是否可以参考先前发的高校考试网脚本建立**本地题库自动测试链接**，不过可能不能用了，你得重新考虑，不知道有没有参考价格。”分层回答：

| 项 | 结论 |
|---|---|
| **那份脚本还能直接用吗** | ❌ **不能**。它是油猴/浏览器脚本（跑在用户浏览器里、题库存 `localStorage`、靠固定选择器点选项），且我们已实测推翻它两条（`#ExamView` 不是视频容器、“六列已完成”不对）；清一下浏览器题库就没了 |
| **那它还有参考价值吗** | ✅ **有，但只剩“结构直觉”**：哪里可能有 iframe、计时以服务端为准、答卷用颜色标正确答案、**“不靠 AI 也能把题库越用越全”的三来源闭环**。具体选择器一律自己测（情报侧 §0.3 第 4 步“只用思路不用字符串”）|
| **价格** | 无价格——两份都是公开仓库/issue 里的免费代码（存档已入 `docs/gxks/`，私有库可存但**仅供内部参考、不可分发**）|
| **“本地题库”我们怎么做** | 存 **SQLite**（清浏览器不丢），key = `question_hash`（sha256(题干+选项)，不用题干原文）；解题链 **`本地题库优先 → AI 兜底 → 考后回收正确答案`**（与超星 `answers(question_hash, account_id)` 同构，表结构可直接复用）|
| **“自动测试链接”的正解** | 依据获授权的页面结构制作**合成数据 fixture**，用于离线解析回归。原始 HTML/截图只存新站私有数据目录，不直接进入 `tests/fixtures/`；入库样本不得含真实姓名、账号、cookie、会话凭据或 WebForms 状态令牌，不为采样反复考试 |
| **回填方式是否一致** | ⚠ **用户已定“待分析研究”，不当定论**。已知差异：超星是“单选/多选点选 + 主观题走 UEditor 富文本写入（含持久化踩坑）”；新站从框架页看是 **WebForms `input[type=checkbox/radio]` + `label` 文本**（C 级情报，待实测），**且交卷走 `__doPostBack`** 而不是我们熟的那套。**开工时先定三件事再写回填**：① 题型集合（单选/多选/判断/填空？）② 选中后平台是否自己记草稿（超星靠 UEditor 暂存）③ 交卷按钮是真链接还是回发。**默认只回填不代交卷**（与超星一致，用户确认后才提交）|

## 五、数据模型预留（后续设计项，本阶段不实施）

用户 2026-10-27 回答：**「是同一批人，但可能是不同学校的人，或者是同一个学校的不同专业，不同年级的，都是多对多的关系。」**

推论（这是设计约束，不是猜测）：

```
自然人 person ─┬─ 平台账号 account（超星 1..N、新站 1..N）     ← 一人多号
              └─ 学籍/机构 enrollment（学校 × 专业 × 年级）      ← 一号多学籍、一学校多专业
```

- **不是"给 `accounts` 加一列 `platform`"就能解决**：真实关系是 `person ↔ platform_account ↔ (school, major, grade)` 三层多对多。
- **跨平台统一视图为后续设计项**：候选方向为按人聚合、按账号调度；并非本阶段实施范围，也不因账号是同一批人就推定已获完整功能授权。
- **画像不能按学校聚合**：现有画像字段假设"平台给姓名 + 学校"（超星），新站同一人可能属于多个学校/专业/年级 → 画像主键必须是 `(person, platform, school)` 三元组。
- **防双开约束的粒度要说清**：超星的"单账号单进程单会话"是**账号级**；一人两平台两账号**不算**双开，同一个平台账号不得同时开多个会话；不同账号并行仍是后续需求，核实阶段仅一个新站会话。

**现在的动作**：保留关系建模需求，**不改超星、不迁移真实数据、不实施整套重构**。核实后首批编码方案先做登录与课程读取，再做单节进度闭环，最后接练习和调度；三层模型与统一视图另行设计。

## 七、运行形态与驱动方式（用户 2026-10-27 新增五条，开工前定死）

用户原话拆成五件事：**① 除了 Playwright 还有没有更高级的、要提前规划成配置项 ② 出问题要有记录、有提示、也要有处理方法 ③ 登录是否还要逆向——待辨别 ④ 新站也要多账号同时运行，前期就规划好 ⑤ 学校要显示，或用学校代号替代（有学校代号库）**。

### 7.1 驱动方式：做成配置项，不绑死一种

**基线现状（2026-10-28，提交 `4e13b9e`）**：Q36 已将 12 处启动调用收口到 `core/browser.py` 的同步/异步工厂。无头优先级是显式参数 > `[stealth].headless` > `True`。因此旧“没有工厂、9 处硬编码、headless 零消费”描述已失效。**尚未支持**可切换 Chrome channel、持久化 profile 或视口档位；已有工厂不等于新站独立 Chrome 会话已接通。本机 Chrome 已安装，但本轮未启动。

候选档位（均为后续设计，使用 Chrome 或持久化目录不保证消除自动化特征）：

| 档位 | 做法 | 能消掉什么 | 代价 / 风险 | 建议 |
|---|---|---|---|---|
| `chromium` | 现状：自带 Chromium + JS 补丁 | 只消表层特征 | **消不掉**：WebGL 仍是 SwiftShader 软件渲染、`outerHeight==innerHeight`、UA 版本与内核要人肉对齐（`stealth.py:13` 自陈"需换真实 Chrome 才能消除"） | 兜底档 |
| `chrome` | `launch(channel="chrome")` 用本机真 Chrome | 使用已安装的 Chrome；渲染与设备能力仍受宿主环境影响 | 依赖本机装 Chrome；版本随用户升级漂移（UA 需现取） | ⭐ 推荐下限 |
| `chrome_persistent` | `launch_persistent_context(user_data_dir=每账号一份)` | 再叠一层"账号身份长期一致"：cookie/localStorage/字体/历史/通知授权都稳定，**多账号之间不串味** | profile 目录要进 `XXT_ROOT` 隔离并纳入备份；崩溃后需能自愈重建 | ⭐ **推荐默认**（多账号场景） |
| `cdp_attach` | 连用户已开的 Chrome（`--remote-debugging-port`） | 接入已有浏览器；不能保证不可检测，不接超星或用户日常 profile | 用户必须常开浏览器，**无法无人值守**；调试端口是本机暴露面 | 只用于"人工辅助登录"环节 |
| `protocol` | 纯 HTTP 逆向（手拼 `__VIEWSTATE` 等） | 无浏览器 | **最不像真人**（TLS/JA3、不执行 JS、无媒体解码）；viewstate 随页面变动而失效；登录能否逆向属未决 | ❌ 不作默认 |

配置形态（草案，开工时定名）：

```toml
[driver]
engine = "chrome_persistent"   # chromium | chrome | chrome_persistent | cdp_attach | protocol
headless = false               # 必须真的传给 launch（超星这条教训：配置写了没人读）
viewport = "match_screen"      # 新站按 screen.width 分流，这条是功能不是审美
profile_dir = "data/profiles/" # 相对 XXT_ROOT；草案尚未被代码消费
```

**架构死规矩**：所有浏览器启动**只准经一个工厂函数**（形如 `core/browser.py: open_context(profile=…)`），adapter 内**禁止**再出现 `chromium.launch(...)`。否则配置项会重演 `[stealth] headless` 的"写了没人读"。

⚠️ **视口对新站是功能问题不是审美问题**：`Default.aspx` 按 `screen.width < 1400` 分流到窄版，而超星现在固定 `viewport/screen = 1280×800`（`stealth.py:83-84`）→ **照搬这套 context 参数，新站永远只会进 `Login.aspx`，进不了 `Loginb.aspx`**。对策⑨ 必须落到代码层的 `match_screen` 或显式 ≥1400，不能停在文档里。

### 7.2 出问题：记录 + 提示 + 处理，三件都必须有

新站业务编码时纳入“记录、提示、处理”三件套；不是本轮环境准备要实现完整面板。下表为可参考的超星基线能力，接入前仍需逐项核实：

| 件 | 超星现状（已核实） | 新站做法 |
|---|---|---|
| **记录** | `run_logs` 四类章节事件 + `auto-*` 事件；`config_audit`（`upsert()` 先比旧值、**值没变不写**）；退避时刻落 `app_config['auto.retry_after']`（带 date，守护重启续跑与面板警示同源） | 同一套；**每次失败额外落一条含机器码的结构化记录**（code / tier / raw_text / evidence） |
| **提示** | 卡片**一行**警示条 `.alertbar`（`nowrap` + `min-width:0` + 省略号 + `title` 放全量），带档位词与"约 HH:MM 自动重试" | 同布局与同"只占一行"约束（超星 Q26 立过规矩：不为警示挤坏卡片） |
| **处理** | `actions_for()` **只给真有接口支撑的按钮**（重新登录 / 立即补跑 / 看日志），刻意不做「暂停 2 小时」「跳过本章」「看截图」 | 沿用该原则（**点了没反应比没有更糟**）；按钮集按新站实际接口重定 |

**关键改进——失败原因出适配层就带机器码**：写失败日志时直接打标签（`[risk]`/`[network]`/`[structure]`/`[login]`/`[crash]`/`[window]`/`[quota]`），面板按标签渲染，中文关键词表**只作兜底**。基线已包含 `run_logs.code`，但并非所有生产者都写机器码，Q27 的关键词兜底仍是超星待办。新站必要的改造先在新站分支完成并测试，不以先修改超星为条件。

### 7.3 多账号同时运行：新站首版就要（用户 2026-10-27 明确）

先修正表述歧义：情报侧 §7.5 对策① 原写"首版不开多开"，**指的是"同一账号多开"，不是"不能多账号"**。两者必须分开：

- **禁止同账号多开**——超星实测里最主要的封号面，新站同规；
- ⚠ **2026-10-29 修正**：“多账号并行是后续产品需求”已过时——用户已确认**首版就要多账号同时运行与调度**。本轮核实期仍仅允许一个新站浏览器会话（D12），产品并发后续另行确认。

三条硬约束（并入 §六 S5 的出口条件）：

1. **账号级会话锁**：一账号一进程一会话（沿用 `core/runmark` 的"标记文件 + PID 归属判定"思路）。锁粒度是**账号**不是人——与 §五 一致：一人两平台两账号**不算**双开。
2. **全局并发上限是配置项，不是硬编码**，且**双限速**：本机资源（用户既有要求：编译/批量等重任务不得占满机器）+ **出口 IP**。新站暂无本轮风控样本，**核实期上限固定为 1 个会话**；产品并发参数另行设计，不把历史“2 账号”建议当已验证安全值。
3. **不以并发或更换出口试探平台底线**：同出口仍共享网络资源；未来并发需依据授权、平台规则与实际资源确定，不把 IP 隔离当安全保证。

**别把已知缺陷复制一遍**：超星的并发是"面板进程内 `_JOBS` + `data/run/<id>.json`"（Q31 定案：面板不开一个都不跑）。新站要不要让**调度器独立于面板**常驻 → 记为 **D9 未决**（它与超星定案会分叉，调度编码前另行拍板，不阻塞本轮隔离核实）。

#### 7.3.1 执行拓扑与默认并发（2026-10-29 定）

一账号 = **一份 `user-data-dir` + 一个 Chrome 实例 + 一个调试端口（9300+序号）+ 一个 worker 进程**（`scripts/watch_gxks.py --port --label`）。不用单进程管多账号：Playwright 同步 API 每步阻塞，一个账号页面重建会拖住全部，且单进程崩=全挂；不用单 profile 跑多账号：cookie 里就写着续播秒数与 `StudentId`，共享即串味。

- **默认串行轮流**（并发=1）：一个窗口跑完一节换下一节，不依赖任何未验证事实，风控暴露最小；
- **并发>1 的前置条件**：必须先用**零风险实验**验掉 Q7/C6（多窗口是否都满足 `hidden=false`），验不过则并发毫无意义（其它窗口一开播就被暂停，属“白开”）；
- **不用手机代替**（Q18 已结案）；
- **算术**：36 节 × 均 ~45 分钟 ≈ **27 小时纯播放/账号**；受“日 10 节 / 600 分钟”闸约束时实际摊到 4 天上下 —— 不因“想快点”就放开日上限（真人一天连看 7.5 小时本身就可疑）。

### 7.4 学校怎么显示：要显示，可用代号（用户 2026-10-27）

用户原话：**「是需要显示学校的，或者学校用代号替代。有学校代号库。」** 落成四条：

- `enrollment` 必须带学校维度，面板"人"这一行要显示学校（真名或代号）；
- **建 `school_code` 字典表**（`code ↔ 学校真名`），直接用用户已有的学校代号库；**真名只放 `data/`（不入库），代号可用于文档、日志、截图、导出**；
- 面板默认口径 → **D8 未决**。我的倾向（推荐）：**面板内显示真名**（要看清是谁的哪所学校），**日志与导出默认代号**（防外传时泄真实学校）；
- **一人多校**（多对多的必然结果）：展示规则定为"首个 + 「等 N 所」，悬浮全量"，与 D8 一起拍板。

### 11.1 路线总览与取舍

| 层 | 选型 | 理由 | 明确不选 |
|---|---|---|---|
| 语言/并发 | Python 3.11 + `asyncio` | 沿用现有栈；面板同生态；与超星 async 定案一致 | 多线程（Playwright 同步 API 禁跨线程）、多进程（仅作逃生舱） |
| 浏览器 | Playwright + 本机 Chrome（`channel=chrome`）+ **每账号持久化 profile** | 平台红字要求 Chrome 形态；profile 长期一致=身份稳定 | 自带 Chromium（WebGL 软渲染等特征）、纯 HTTP 逆向（`protocol`） |
| 平台适配 | 独立包 `adapters/gaoxiaokaoshi/` | 核心层零平台细节；与超星同规格边界守护 | 改 `session/`、`core/` 去兼容第二平台 |
| 存储 | SQLite（WAL），新站独立库 | 零运维、单文件备份；账号量未知但非高并发写 | MySQL（规模未到）、复用超星库（数据分叉） |
| 后台执行 | 独立 runner 进程 + DB 指令表 | 面板重启不打断学习；状态可跨重启恢复 | 面板进程内 `_JOBS` 字典（超星现状，重启即失联） |
| 面板 | FastAPI + 轻量 HTML | 现有实现可参考；不引前端框架 | 前端 SPA 重构 |
| AI | OpenAI 兼容接口，异步 httpx | 换厂商零改码；与超星 Provider 中心同构 | 绑定单一厂商 |
| 测试 | pytest + 合成 fixture + 模拟时钟 | 真实页面含 PII 与状态令牌，不得入库 | 真实 HTML 转储做回归样本 |

**依赖方向死规矩**（新增静态断言守护，不改超星既有断言）：

1. `core/` 不得 import `adapters/*`；
2. `adapters/gaoxiaokaoshi/` 不得 import `adapters/chaoxing/*`；
3. 浏览器启动只经 `core/browser.py` 工厂，adapter 内禁止出现 `chromium.launch(...)`；

```
      ├─ 有效 → 直接进课程，不产生登录行为
      └─ 失效 → 检查当日登录预算
            → 解密本机凭据（AES-GCM）
            → 真浏览器填表单、点提交（不逆向 HidLogin.aspx）
            → 判定结果
                ├─ 成功 → 回写会话，续原任务
                ├─ 网络/503 → 有限退避重试（3 次封顶 + 抖动）
                ├─ 密码错误 → 停止重试，标记凭据待修
                └─ 验证码/风险页 → 分级处理（下表）
```

**验证码分级**（无样本前不得承诺“全自动通过”）：

| 级 | 形态 | 处理 |
|---|---|---|
| A | 固定 4 位图形码（历史记录过 `VerifyCode.ashx`） | 尝试自动识别；连续失败即转人工，**不无限试错** |
| B | 滑块、短信、扫码等交互/实名验证 | 不尝试破解，直接转人工接管 |
| C | 未知弹层或未知提示 | 停止自动操作，落证据并要求样本后再定 |

**硬性约束**：

1. 每账号每日真实登录尝试 ≤ `login.budget_per_day`（默认 2，含失败）；耗尽即冷却转人工；
2. `needVerify=1` 一类风险标记出现即停自动登录，不重复提交；
3. 登录成功判定必须用**平台真实标志**（登录后页面特征/会话 cookie），不能用“点击已执行”；
4. 登录结果、失败原因、机器码全部落 `run_logs`，凭据与 cookie 零记录；
5. **人工接管后可自动恢复**：验证完成后系统续跑原任务，不要求重新排队或重配。

### 11.4 数据模型（增量，不改超星库）

**关键约束**：现有 `store/db.py::connect()` 每次连接都执行共享 `_SCHEMA` 与补列迁移——**对超星库同样生效**。因此新站对象一律走独立迁移：

- 新表新列写在 `store/schema_gxks.py`，由新站入口在连接后显式调用；
- 版本号用独立键 `meta.gxks_schema_version`，**不动共享 `SCHEMA_VERSION`**；
- 超星库即使被新站代码打开，也不会多出任何表或列。

| 对象 | 性质 | 说明 |
|---|---|---|
| `accounts` / `courses` / `run_logs` / `app_config` | 复用 | 字段够用；不加列 |
| `gx_sections` | 新增表 | 节粒度：`plan`、`section_no`、`required_minutes`、`done_minutes`、`state_text`、`practice_unlocked`、`raw_text`（先存原文再解析） |
| `groups` / `account_groups` | 新增表 | 多选自定义分组；一账号多组 |
| `runs` | 新增表 | 任务指令与状态（`queued/running/stopping/stopped/done/failed/blocked`），跨重启恢复 |
| `schedules` | 新增表 | 定时计划与暂停标志；与 `runs` 分离 |
| `gx_q_types` | 新增表 | 题型字典（14 种，`code` + 中文名），取自平台 `tx_arr` 实测 |
| `gx_q_items` | 新增表 | **题目版本**：`UNIQUE(platform_qid, fingerprint)`；`fingerprint` = sha256(题型 + 题干 + 题干 HTML + 部件 + extra)。题 ID 相同但内容或选项顺序变了即算**新版本**，避免答案字母错配 |
| `gx_q_parts` | 新增表 | **部件表** `(item_id, ordinal, kind, part_key, content_json)`：题干 / 选项 / 材料 / 子问由部件承接，**新题型不改表结构** |
| `gx_q_papers` | 新增表 | 一次答卷：`account_label`、`exam_start_id`、`exercise_id`、`course_id`、`section_id`、`section_name`、`paper_label`、`start_time`，`UNIQUE(account_label, exam_start_id)`。**字段口径（2026-10-30 定）**：`section_id` = 课程列表行里 `showframe('节名', 节ID)` 的数字（真正的节粒度主键）；`course_id` 暂存**平台课程名**（如“军事理论（字幕版）”）——`ddlClass` 的 value 尚未采集，存名字既稳定又可直接分组 |

| `gx_q_answers` | 新增表 | 逐题作答证据：`picked_json` / `standard_json` 及各自 `*_source`（`human`/`site`/`ai`）、`score_got`、`is_correct`、`explanation_html`；主键 `(import_id, ordinal)` ⇒ **新判分追加、不覆盖旧答案** |

题干可共用、答案不可共用——沿用超星 2026-10-26 定案。用户要求“碰到的题自动收库供后期检索”，只放宽**题干**，不放宽**答案**。

**已落地实现**：`store/schema_gxks.py`（`GXKS_SCHEMA_VERSION=2`，7 张表 + 3 索引；拒绝降级打开、拒绝带未提交事务、`open_question_bank()` 见到 `accounts` 表即拒）+ `store/gxks_questions.py`（`import_bundle` 幂等、`read_attempt`、`bank_counts`、`backfill_classification`、`bank_items`）+ `adapters/gxks/practice.py`（`parse_capture` 交叉校验 + `section_index` 反查节 ID）+ `scripts/import_gxks_practice.py`（离线导入，`--dry-run`）。导入只存**来源文件 sha256**，姓名 / 学号 / ViewState 不入正式题库。

**2026-10-30 三处修正**（对应 `docs/devlog/2026-10-30-02-gxks-bank-defect-fixes.md`）：

1. **分类字段不再为空**：练习页 URL 只带 `Tk_Cl_Id`（练习 ID），**没有节 ID**；原实现把 `course_id` / `section_id` 硬写成 `""`。现由 `section_index(course_doc)` 从课程列表快照按 `showExam(练习ID)` 反查 `showframe('节名', 节ID)`，同时校验两侧节名一致。
2. **幂等键只含内容**：`_content_digest` 只取 `exam_start_id` / `exercise_id` / `questions`；`course_id`、`section_id` 一类元信息变更**不再产生新快照与重复答案**（enrich UPDATE 提前到幂等判定之前）。
3. **跨节同题可归并**：`gx_q_items` 仍按 `UNIQUE(platform_qid, fingerprint)` 保留证据，新增 `fingerprint` 索引；导出/检索走 `bank_items()`，同一指纹只出一条并带 `occurrences` 与 `platform_qids`。

历史数据用 `backfill_classification()` 补（只填 `NULL`/空串，不覆盖已有值，幂等）：2026-10-30 已对库里唯一一条答卷补成 `course_id='军事理论（字幕版）'`、`section_id='1289'`，快照数保持 1。

### 11.5 控制协议与启停语义

| 指令 | 语义 | 幂等 | 结果回报 |
|---|---|---|---|
| `start(account, source=manual\|schedule)` | 无活动任务则启动，否则按并发上限排队 | 是（已有 runs 记录即返回同一 id） | `run_id` + 状态 |
| `stop(account)` | 只停本次执行并取消本次重试；**不动 `schedules`** | 是 | 先“停止中”，后台确认退出后“已停止” |
| `schedule_pause` / `schedule_resume` | 只控制未来触发；不影响当前任务与手动启动 | 是 | 计划状态 |

- 界面区分三种不同状态：**计划关闭 / 计划暂停 / 任务停止**；
- 无启用计划时隐藏暂停按钮；已暂停后必须显示“恢复定时计划”（否则无法恢复）；
- 恢复不补跑错过的时段；暂停期间已排队的自动项不得启动，手动项不受影响；
- 停止超时须显式报错，不能静默显示“已停止”。

### 11.6 配置项清单（草案，开工时定名）

```toml
[driver]
engine = "chrome_persistent"   # chrome | chrome_persistent
headless = false               # 必须真的传给 launch
viewport = "match_screen"     # 低于阈值会换登录页形态
profile_dir = "data/profiles/"

[runtime]
mode = "standalone"            # standalone(独立后台) | with_panel(随面板)
max_concurrency = 10           # 【同时运行数】= 10 个账号同时跑。2026-10-29 用户暂定 10；可配改
fleet_daily_minutes = 0        # 【全部账号合计】总量闸，0=不限

[login]
budget_per_day = 2             # 【每账号】含失败；1~5
captcha_auto = false           # A 级验证码自动识别开关（默认关）

[gxquota]
daily_tasks = 10               # 【每账号】日学习任务（节）上限。0 = 不限。2026-10-29 暂定 10，用户自行可改
daily_minutes = 600            # 【每账号】日时长上限。0 = 不限。非 0 时必须 >= daily_tasks × 单节上限(60)
```

⚠ **两个闸是“任一达标即停”，必须一起算**（审核补充）：若保留旧值 `daily_minutes=240`，账号到 4~5 节就被时长闸提前停，`daily_tasks=10` 永远碰不到。所以两项必须联动：

| 想要的节数 | `daily_tasks` | `daily_minutes` 至少 |
|---|---|---|
| 2 节 | 2 | 120 |
| 6 节（满一轮） | 6 | 360 |
| **10 节（本次暂定）** | **10** | **600** |

**`0` = 不限，允许用户自己改（用户 2026-10-29 明确：“也可以设置不限、全改为 0，根据需求来设置”）**。已在代码核对，**学习引擎侧口径一致**：`sample_daily_budget` 遇 ≤ 0 返回 0；调用处用 `if budget_tasks:` / `if budget_minutes:` 跳过判定；`quota_reached` 用 `bool(budget_minutes)` 判。三处都成立，所以 0 确实等于不限。

⭐ **更根本的修法：把“上限”和“达成”解耦（2026-10-29 定，取代“禁止 0/0”的临时约定）**

问题根源：超星把同一个额度**既当刹车又当终点**。`reached_locally()` 在两项都为 0 时返回 `True`（原注释：“两项都不限 → True”），于是“不设限”被读成“今天已经学够” → 定时不触发。**这不是 0 的错，是两种语义挤在一个数上。**

新站把两件事分开：

| 概念 | 含义 | 由谁决定 |
|---|---|---|
| **当日目标** | 学到几节算“今天完成” | 平台剩余待学节 + 当天计划，**自动算，不配置** |
| **上限** | 最多允许多少，防学过头 | `daily_tasks` / `daily_minutes`，**0 = 不设上限** |

- 达成判定 = **当日完成节数 ≥ 当日目标**，不读额度；
- 额度只在“意外多学”时刹车；
- 因此 `0/0` 也安全：目标仍由平台剩余决定，不会出现“一开跑就判今天已学够”。

**硬约束**：新站**不得复用 `core/quota.py::reached_locally()`**（它把 0 读成“已达”），只复用 `sample_daily_budget` / `remaining_minutes` / `sum_done_seconds` 这类纯计算。列入 T4 验收项。

**为什么不用 `-1` 表示不限**（更常见的约定，但不适合这里）：① `core/quota.py` 是超星与新站**共享**的，改语义会波及超星现状（红线）；② 两平台两套方言，后来者必然搞错；③ 共享代码三处已一致实现 0 = 不限，照用即可。

**四组预设（改配置即可切换，不改代码）**：

| 预设 | `daily_tasks` | `daily_minutes` | 效果 |
|---|---|---|---|
| **按节数管（现暂定）** | **10** | **600** | 两闸联动，节数为主 |
| 只按节数管 | 10 | 0 | 不限时长，只限节数 |
| 只按时长管 | 0 | 600 | 不限节数，只限时长 |
| 全放开 | 0 | 0 | **安全**：目标仍来自平台剩余待学，学完当天就停 |

⭐ **额度口径必须分清（2026-10-29 人工确认 + 代码核对）**：

| 概念 | 归属 | 防的是什么 | 超星现有实现 |
|---|---|---|---|
| `gxquota.daily_minutes` | **每个账号各自一份** | 单账号行为异常被封 | 已如此：`astudy.py` 按 `run_logs.account_id` 聚合当日 `video-done` 秒数；`accounts.daily_max_minutes` 可单账号覆盖 |
| `daily_tasks` | **每个账号各自一份** | 同上 | 已如此（双额度，任一达标即停） |
| `runtime.max_concurrency` | **全局** | 本机资源 + 出口 IP 并发特征 | 超星无此项，新站新增 |
| `runtime.fleet_daily_minutes` | **全局合计** | 设备/IP 维度“一天总时长异常” | 无，**新站新增（建议不开，但要有）** |

推论：**总消耗 = 账号数 × 当天实际学时**（不是乘“上限”）。上限只是天花板，不消耗机器时间；实际消耗看当天学了多少：30 个账号 × 一轮 300 分钟 = 9000 分钟 = **150 机器小时**，并发 10 → 摊到 **15 小时**（§11.11）。

节级“学时要求”来自平台页面，**不做配置项**（配置它等于允许伪造达标）。

⚠ **配置落地注意**：新增节必须同时进 `config.py::DEFAULTS`（否则面板/审计看不到默认值），并在面板的配置中名词表里登记中文名（超星 Q41/Q42 的“最近配置变更”靠它），否则面板会出现看不懂的英文键。

### 11.9 风险与诚实边界

| 风险 | 事实 | 对策 |
|---|---|---|
| **登录链路为明文 HTTP** | 2026-10-29 实测：页面 `Login.aspx`、表单 `POST http://www.gaoxiaokaoshi.com/HidLogin.aspx`；HTTPS 不可达 | 本地 AES-GCM 只保护静态存储、**不保护传输**；仅自有网络、不做代理转发、日志零凭据；用户 2026-10-29 已知悉该风险并同意继续 |
| 验证码能力未知 | 本轮零样本 | 分级 §11.3；A 级默认关，失败即转人工；不承诺全自动 |
| ~~计时口径未知~~ → **已实测（2026-10-29）** | 计时 = **页面墙钟**（`m_time` 每秒 +1，**不读** `video.currentTime`），每 **60 秒**向 `updateTime.ashx` 上报一次累计秒；`visibilitychange` 切后台即 `player.pause()` 停表 | 见 §11.13 的 C1~C6：**倍速确定无效**；不拖进度、不伪造上报、只触发一次 `play` |
| **单账号耗时刚性** | 每节 42~45 分钟（实测）、一轮 **36 节** ≈ **26 小时**，无法倍速压缩 | 多账号必须排队错峰；并发上限受本机资源与出口双重约束；**不得把并发当成提速手段** |
| 选择器易变 | WebForms 页面随时改版 | 选择器外置 `selectors.toml`；改版只改配置 |
| 独立后台常驻 | Windows 下会话结束可能被回收 | 用任务计划/服务方式启动；不在沙箱终端里 `Start-Process` 起长驻进程 |
| 个人身份差距 | 平台按屏幕宽度分流登录页，本轮 1920 宽却落 `Login.aspx` | 分流规则**未证实**，不照抄历史阈值；以实测为准 |

### 11.10 本节自审结论

**已在本文修正的问题**：

1. **共享迁移会波及超星库**——原设想“直接给 `chapters` 加列”会在超星库执行 ALTER；改为 `store/schema_gxks.py` 独立迁移 + 独立版本键。

### 11.11 容量测算与待决问题（审核补充）

**刚性耗时**（2026-10-29 登录后实测修正）：单节 **42~45 分钟**（平台“学时要求”列直接给分钟，见 `gaoxiaokaoshi.md` §2.8），按服务端时钟计、**不能倍速**。⚠ 历史“一轮 6 节 ≈ 285 分钟”的假设**已被推翻**：实测列表 4 页 × 9 行 = **36 节**（2026-10-29 逐页翻完），整轮 **约 26 小时**。

通俗口径（为什么并发=1 时一天只服务 7~8 个）：一节视频必须真等满，机器是“陪着等”不是“算得快”；并发=1 等于**只有一个洗车位**，一辆车 45 分钟，一天洗完几辆是固定的，催不快。**唯一提速手段是加车位（提高并发），不是催洗车工。**

**按实测单节 44 分钟、15 小时窗口（900 分钟）重算**：

| 每账号当天实际学 | 单账号耗时 | 并发 1 | **并发 10（现定）** |
|---|---|---|---|
| 2 节 | 1.5 小时 | 约 10 个 | 约 100 个 |
| 6 节 | 4.4 小时 | 约 3.4 个 | 约 34 个 |
| 10 节（当前上限） | 7.3 小时 | 约 2 个 | **约 20 个** |

⚠ **结论变了**：上一版“30 个账号一天跑完一轮”**不成立**。按 10 节/账号/天、并发 10，30 个账号合计 300 节 ≈ **220 机器小时 ÷ 10 = 22 小时**，已顶满一整天；而一轮 **36 节**，因此**整轮约需 3.6 天**。要更快只有两条路：提高并发（风控未知）或降低每账号日节数（周期更长）。

| 每账号日节数 | 单账号耗时 | 30 账号合计 | 并发 10 需时 |
|---|---|---|---|
| 2 节 | 1.5 小时 | 44 小时 | 4.4 小时 |
| 6 节 | 4.4 小时 | 132 小时 | 13 小时 |
| 10 节（现定） | 7.3 小时 | 220 小时 | 22 小时 |

⚠ **口径提醒**：所有“日上限”都是**每个账号各自一份**（依据见 §11.6 额度口径表），所以账号数会成倍放大总耗时。

结论（必须让用户知道的产品事实）：

1. **日上限低于单节要求时，进度会停在半节**——不是 bug，是配置结果；日上限应至少 >= 2 倍单节要求，否则看起来“永远学不完”。
2. **整轮不是 6 节而是 36 节**：按 10 节/天、并发 10，30 个账号约需 **3.6 天**跑完一轮；想一天一轮只能把每账号日节数抬到 36（不推荐，单账号日在线超 26 小时，不可能）。
3. **提高并发是缩短周期的唯一手段，但它同时是未知风控面**——本轮无样本，不得先调高再观察底线。

### 11.13 播放与计时的实测结论 → T4 硬约束（2026-10-29）

> 平台事实见 `gaoxiaokaoshi.md` §2.10，本节只写“因此代码必须怎样”。

| # | 约束 | 理由（实测） |
|---|---|---|
| **C1** | **必须 `headless=false`，且窗口不得最小化、不得切标签** | `visibilitychange` → `document.hidden` 时站点自己 `player.pause()` 并停表；无头/最小化直接等于“学了 0 分钟” |
| **C2** | **只触发一次 `play`**；不重复调用 `play()`、不在播放中 `seek` | `m_time` 是全局变量，每次 `play` 事件都新起一条计时链且不清旧链 → 重复 play 会把上报的 `pTime` 拖快，产出**异常数据**（正是风控最擅长发现的那种） |
| **C3** | 不倍速、不拖进度、**不伪造 `updateTime.ashx`** | 计时是墙钟，倍速省不了时间；伪造上报直接违反“不硬闯风控” |
| **C4** | 完成判定只认**列表回读**（`已完成学时` + 状态文案），不认本地计时 | 超星“假完成”教训；且服务端口径未知（本次 10 分钟 vs 播放 7 分钟），本地推算必错 |
| **C5** | 卡缓冲不补偿；但每次巡检要断言 `player.paused === false`，被暂停则恢复**一次** | 卡顿不触发 `pause` 时表继续走，无需补偿；而 `pause` 会停表，不恢复就白等 |
| **C6** | 前台窗口是**稀缺资源**，与并发直接冲突 | 一屏只有一个前台窗口；⚠ “多个不最小化的窗口是否都不触发 `hidden`”**未实测**，必须在 T6 前用小规模（2~3 窗口）验证；若验证失败，并发模型要改成“轮转前台”（每账号独占时间段） |
| **C7** | 巡检看到 `video` “不动了”必须**分三种情况处理**：① **媒体重建** → **重载播放页开新会话**（⚠ 原写“不干预、等自恢复”，已被 **Q13** 推翻：重建后服务端**停止记账**，继续挂 = 白挂）；② 真暂停 → 恢复**一次**；③ `hidden=true` → 立即恢复窗口并告警。⚠ 重建的**判据不能用 `paused`**：实测重建既出现过 `paused=True`、也出现过 `paused=False`，应以 `d=None` 且“先有后无”或 `t` 回退 > 5 秒为主 | 重建时贸然 `play()` 会多起计时链（与 C2 冲突）；不重载则学时不再增长（Q13）；真暂停不恢复则白等（与 C5 联动） |

| **C8** | **允许锁屏、允许被其它窗口完全遮挡（叠放）；只有“最小化 / 切到后台标签”才会 `hidden` 停表** | ① **锁屏**（2026-10-29 11:50）：`Win+L` 锁定 **185.9 秒**，`clock` 88→274（**+186，1:1**），期间 `paused=False`、`document.hidden` 全程 false、`LogonUI.exe` 在线 ⇒ 锁屏不触发 `visibilitychange`。② **完全遮挡**（2026-10-29 13:27，`data/debug/exp_occlusion_timer.py`）：两个**同位置同尺寸**的窗口置顶叠在播放窗口上，60 秒里 `clock` 1683→**1746**（+63）、`paused` 恒 False、`hidden` 恒 False，且 **`hasFocus` 全程 False 也不影响**；同时被盖住的窗口里 `setInterval(1000)` 计到 **60/60** ⇒ **被遮挡的窗口不被 Chrome 节流**（只有最小化/切后台才节流 + `hidden`）。③ 早前“锁屏会停表”是**误判**（当时播放器本就已暂停） |
| **C9** | **学时按“累计播放时长”计，与视频进度脱钩**；已达标的节**不得再播** | 1.1 视频 2871 秒（47.85 分钟），列表已达 **236 分钟**（要求 45）：08:45 确认 54，到 11:49 共 +182，而视频只前进 13 分钟（多次重载/续播）。⇒ 重复播会持续加学时，形成“学时 ≫ 视频长度”的异常数据 |
| **C10** | **达标后必须“离开播放页”（导航走），不得只调 `pause()`** | 2026-10-29 12:32 守播达标后调 `player.pause()`，5 秒后复查 `paused=True`（确实停了）；到 12:37 量表 43→**48**，且 `t` 由 2166 回到 **65**、`d` 由 2614.41 变 2615（新 MediaSource）⇒ **暂停期间发生媒体重建，播放器自行恢复播放**；又因 `stopLoop()` 只置 `playFlag=false`、**不消 `m_time`**，`player.on('play')→myload()` 一触发就从原值继续累加 |
| **C11** | **达标必须留余量：`已完成学时 ≥ 学时要求 + 2 分钟`，不停在“刚刚好”**（`OVERRUN_MARGIN_MINUTES`，`--margin` 可改） | 2026-10-29 用户明确要求：“已完成学时要比学时要求多一点，不能是刚刚好”。机制上这个余量不是保守而是必需：最后一分钟的 `updateTime` 一旦碰上 503/断网就不入账（R1 只能对单次抖动自愈），停在等号就会卡在 `要求-1`，表现为“视频播完了却还是学习中”，而 `ended` 后再也不会补播（C9/时间已用尽）。配套：距目标不足 10 分钟时回读加密到 **60 秒**，避免“5 分钟一回读”把余量拖成多跑 5~7 分钟（36 节会白跑 4 小时） |

**由 C6 引出的新风险（写在这里以免忘）**：若为省内存把窗口最小化，所有计时会**静默归零**（表现为“跑了一整夜一节没学完”）。所以 T4 起就要有**本地校验**：`updateTime` 是否按 60 秒节奏出现；节奏断了要**告警**，不得静默继续。

**本次实测同时带来的好消息**：站点**没有**鼠标/键盘活跃度判定、没有倍速/拖进度检测、没有指纹 SDK —— 所以“拟人化鼠标轨迹”这类工作量可以省掉，真正要守的只有 C1~C3 三条“别碰机制”的红线。

**总验收口径（用户 2026-10-29 拍定）**：不看实现细节、不做学理验证，**只看列表「已完成学时」是否只涨不跌、达到「学时要求」后状态转「已完成」**——这一条成立即算可用。下面 Q12/Q13 只保留**能直接影响这条口径**的部分。

### 11.16 多账号与多课程（2026-10-29 落地第一半）

**目标**：用户问“是只固定这一门课、这一个人用，还是可以多人用、可选不同课程”。结论先摆：

- **多个人用：能做，已落地骨架**——账号表 + 串行调度 + 失败隔离。
- **多课程：代码已就绪，但今天验证不了**——这个账号的课程下拉只有 1 项（军事理论，见 Q30）。

#### 分层（谁干什么）

```
run_gxks_multi.py            外层：读账号表 → 额度预检 → 端口探活 → 逐账号/逐课 起子进程
  └─ run_gxks.py              内层：一个账号 —— 挑节 → 守播 → 达标 → 记账 → 歇 → 下一节
       └─ adapters/gxks/driver.py   页面操作（列表/翻页/课程/播放）
            ├─ accounts.py            账号表（读数 + 校验 + 回落老单账号）
            └─ ledger.py              运行账本（当日节数/分钟，日额度唯一依据）
```

#### 账号表 `data/accounts.local.json`（gitignore）

```json
{
  "accounts": [
    {"label": "jia", "display": "甲同学", "name": "<账号>", "pw": "<密码>",
     "port": 9222, "profile": "D:/xxt-profiles/jia",
     "courses": [32], "daily_sections": 10, "daily_minutes": 600, "enabled": true},
    {"label": "yi", "display": "乙同学", "port": 9223, "profile": "D:/xxt-profiles/yi"}
  ]
}
```

规则：

- `label` 只能 `[a-z0-9_-]`（代号制，进日志/文件名）；**真名只放 `display`**，不得进文件名。
- **一账号 = 一端口 = 一 user-data-dir**（§7.3.1）：保证 cookie/会话互不覆盖。
- `courses` 空 = 跑该账号能看到的全部课程；写 `[32]` 只跑这一门。
- `name`/`pw` 可空：空 = “无凭据”，掉登录就停（不自动重登），比乱试安全。
- **没有这个文件时自动回落到老的 `data/account.local.json` 单账号**（`label=default`、端口 9222），已跑通的流程不受影响。

#### 日额度与账本（为什么必须本地记账）

站点只给**累计学时**，**查不到“今天学了几节”**（列表无日期、无接口）。所以：

- `ledger.py` 每跑完一节追加一行到 `data/gxks_ledger.jsonl`（`date/account/section_id/minutes/result`）；
- 只追加、不重写；`account + section_id + date` **去重计数**（重跑不重复扣额度）；坏行跳过；
- 开跑前读当日合计：额度不够 → 直接 `[SKIP]`；够 → 把 `--max-sections` 收敛到剩余节数。

⚠ **账本 2026-10-29 当天上线，历史未追溯**：今天已完成的 1.1~2.2（共 11 节）不在账本里，所以今天显示的“已 0 节”偏少；**次日零点起准确**。不补录是有意为之：补录 11 节会立刻把今天的额度判成“用完”，今晚反而跑不了。

#### 失败隔离（多个人用时的关键）

| 情形 | 处理 |
|---|---|
| 某账号 CDP 端口没开 | 打印起浏览器命令（`--remote-debugging-port` + `--user-data-dir`），**跳过该账号**，不拖整批 |

| 某账号额度用完 | 跳过，汇总里注明 |
| 课程切不过去 | 停该账号（不猜、不重试），报 `切不到课程 <value>` |

```
  → 读题（哪个帧有 tm_arr 就是答题帧，不认帧名）
  → 题库优先（只认 standard_source='site'：平台判分过的客观答案，AI 答案不跨账号借）
  → LLM 兜底（复用 Provider 中心）
  → 真点击 radio（onclick=check_index(N) 刷新答题卡；只置 checked 平台算没答）
  → 回读校验（选了哪些就应读到哪些，对不上即报错，不把“部分填好”当成功）
  → 停住，等人核对
```

边界（三条都是“宁可停也不猜”）：

1. **默认不交卷**：`[gxks] auto_submit = false`。技术上 `frmExam.submit()` 不经过交卷按钮的 confirm，所以自动交卷**能**做到；但没人在场就没人看答案对不对 —— 按用户定的「后面测试成熟后可以转为自动提交」先关着。
2. **题型白名单**：`[gxks] allowed_types = "2"` 只放**单选**（已实测）。遇到 3=多选 / 4=判断 / 其余 11 种未实测题型 → **整卷停**（`WorkError('structure')`，退出码 4），不装懂。
3. **答卷不重复建**：每点一次「参加练习」服务端就新建一份（Q32），所以面板按钮不做“先看看”的语义，按一次就是一次。

### 12.5 已知限制（不假装做完）

1. **AI 回填尚未在真实环境跑过**：本次只完成代码 + 合成 fixture 测试（真实结构、合成题干）。首次实跑需要 Chrome 已登录 + 服务端真的建卷。
2. **打包成 exe 后起不了任务**：`scripts/` 不在 exe 包内，`_start()` 会明确回“打包版面板暂不支持起脚本”，不会默默 500。
3. **UI 是单账号视图**：右上角下拉切换账号，没有同屏多账号对照；账号增删改仍改 `accounts.local.json`。
4. **`gx_ops` 与超星 `run_logs` 不合并**：两边账号主键不同（`account_label` vs `accounts.id`），合并需维护映射，不值得。

## 十三、部署形态、提交确认与超星兼容边界（2026-10-30 设计定稿）

### 13.1 平台硬事实：练习回填**没有草稿**

用户实机确认：「这个平台里面的回填是没有保存的，要么直接提交，要么退出」。代码侧对得上：草稿路径 `SaveMode=0` 只存在于 `btnCancel_onclick()`，**界面上没有保存按钮**（Q28 实测）。

⇒ **练习作答必须单一环境闭环**。原先设想的“Docker 回填 → 本机交卷”**作废**：没有草稿就没有跨环境的桥。

### 13.2 三种作答形态（差别只在“最后那一下谁点”）

| 形态 | 谁点交卷 | 环境 | 前提 / 风险 |
|---|---|---|---|
| **A 半自动** | 人，在同一窗口核对后点 | 本机有头 Chrome | 脚本填完必须**断开 CDP**（Q31：连着会吞 confirm） |
| **B 全自动** | 脚本 | 容器 / 无头均可 | `auto_submit = true`，答错风险自负 |
| **C 面板确认**（新增，推荐） | 脚本，但由人在**面板**点「确认提交」触发 | 本机或容器均可 | 回填后断开 CDP → 面板展示整卷 → 人点确认 → 脚本重连、注册 dialog accept、点交卷、读分入库 |

C 的两条硬约束：

1. **窗口期内页面不能关、不能刷新**——无草稿，关了答案就没了；
2. 点确认后**先回读校验**（radio 是否仍被选中），对不上就重新回填再交，**不把“填了但丢了”当成功**。

### 13.3 刷课与练习分开部署（不是一件事劈两半）

- **刷课**：播放 → 达标 → 记账 → 歇，无人中间态 → **天然适合容器**，全自动。
- **练习**：有“人点交卷”这个必须中间态 → 按 13.2 的 A/B/C 三选一。

### 13.4 容器对外提供同一套面板（可行，三个前置）

同源：容器内 `python -m xxt.cli gxks-panel`，宿主映射 8301，浏览器打开即**同一个 UI、同一套 API**。前置：

1. **监听地址**：`serve()` 读 `[panel] host`，现为 `127.0.0.1` → 容器只绑回环，`-p 8301:8301` **转不进去**。必须 `0.0.0.0`，且要能由 `XXT_PANEL_HOST` / `XXT_PANEL_PORT` 覆盖（否则又得改共享 settings.toml）；

3. **“看得见的窗口”**：无头容器里没人能点交卷 → 只能走 B 或 C；真要窗口需 noVNC，本阶段不排期。
