## 一、定位与总原则

- **独立排期线**：与超星主线（P0~P3）**不交叉、不并行推进、不互相借用结论**。用户 2026-10-27 原话：「可以单独排期，不和现在的进度交叉，等目前这个超星项目差不多再入手……最好不要互相影响。」
- **规则先于动手**：用户 2026-10-27 原话：「**做好规则再动手**。」→ 本文与 `gaoxiaokaoshi.md` 就是"规则"的载体；规则没落地成文之前，不写一行 adapter。
- **当前状态**：**已规划、未立项、未开工、未实测**（除公开页特征/跳转链的只读探查）。本文**不是开工许可**。
- **操作方式与超星一致**（用户提问已答）：真浏览器 + 点真实 DOM + `pace` 拟人化节奏 + 不逆向 POST。但**理由不同**：超星是"策略选择（对抗行为风控）"，新站是"技术必需"（ASP.NET WebForms + `__VIEWSTATE` + iframe 套壳 + 客户端 JS 分流，无 API 可打）。详见 `gaoxiaokaoshi.md` §7.4 / §7.5。

## 三、⭐ 开工前必须"再核实一次"——硬性门禁（用户 2026-10-27 新增）

用户原话：「这个可以落规划，但**后期真正开始之前必须还要再核实一次**。」

因此定为**门禁而非提醒**：G1~G4 满足、准备开第一个 `feat/gxks` 提交之前，必须先跑完下表并把结果写回 `gaoxiaokaoshi.md`，**任一项不过就停在侦察阶段，不写 adapter**。

| 核实项 | 怎么核实 | 不过怎么办 |
|---|---|---|
| R1 **版本指纹** | 登录后第一件事记录 HTML 内资源版本串（`?tmp=`、bundle 名、`<meta generator>`）与抓取日期，写入档案头部 | 指纹与本文档记录不一致 → **本档案所有 C 级条目视为全部重测** |
| R2 **登录链路仍成立** | 复核 `Default.aspx` 的 UA/`screen.width` 分流是否还是 `Login`( <1400)/`Loginb`(≥1400)/`Loginm`/`Loginp` 四支；`needVerify` 参数名是否变化 | 分流规则变了 → 重定登录策略，UA/视口档位重新标定 |
| R3 **凭据形态没变** | 仍是学号+密码+可选图形码？是否新增短信/实名？ | 若加短信 → `login_budget_per_day` 与人工介入流程需重设计 |
| R4 **服务端"暗地里"的判定规则** | 一个账号人工正常节奏跑，观察什么行为后开始被要求 `needVerify`（IP 频次？时长？并发？错密？） | 拿不到结论 → 首版额度按超星的 **50% 起步**（不放宽） |
| R5 **目录/端口/数据隔离仍合适** | 见 §四，届时按用户当天习惯重定 | 未确认前**不得开工**（曾出现 `XXT_ROOT` 未设导致新站读写超星真实 `data/` 的风险） |

> 这条门禁存在的原因：本文档写于**未登录状态**，读者是"未来那条没有今天上下文的会话"。它极可能把 C 级情报（第三方 2020~2025 年的脚本推导）当事实抄进代码。门禁就是把"必须先重测"变成机器可查的步骤。

## 四、隔离方案（代码/数据层为暂定值，R5 复核后定稿；**文档层已定**）

五层隔离，全部沿用仓库既有 SCM 约定（一目录一分支 + `git worktree` + `XXT_ROOT` 数据隔离；**不新建仓库**）：

| 层 | 值 | 作用 |
|---|---|---|
| **文档（✅ 已定 2026-10-27）** | 本项目全部资料集中在 **`docs/gxks/`**（本文件 + `gaoxiaokaoshi.md` + 第三方脚本存档）；**超星台账不记 Q35，devlog 不写新站细节，只允许 STATUS §3 一行指针** | 读超星文件时撞不到新站结论，避免把 C 级情报当超星事实；同时仍在 git 备份内（不降低 durability） |
| 分支 | `feat/gxks`（`main` 只走超星） | 代码不混 |
| 工作树 | `git worktree add E:\xxt-gxks feat/gxks`（暂定） | 目录不混、可同时打开 |
| **数据** | `XXT_ROOT=E:\xxt-gxks-data`（暂定） | **最关键**：绝不让新站碰超星真实 `data/`（账号、`xxt.db`、`lic`、cookie） |
| 面板端口 | **8301**（超星 8300 不动，暂定） | 两套面板可同开，不打架 |

**三条防污染硬规矩**（任何会话动 `feat/gxks` 都受约束）：

1. **核心层改动权在 `main`**：`core/` `store/` `panel/` `cli/` 如需为多平台解耦，必须**先在超星主线改并验证**，再合并进 `feat/gxks`；不得在分支上顺手重构核心层。
2. **`tests/` 是超星红线**：新站只新增 `tests/test_gxks_*.py`，**不得修改**现有测试文件来"让它通过"。
3. **开工前先还清 Q27**：带着未完成的收尾进分支，等于把两条线的烂账混成一团。

## 五、数据模型预留（⚠️ 唯一必须"趁早定"的事，因为动的是核心层）

用户 2026-10-27 回答：**「是同一批人，但可能是不同学校的人，或者是同一个学校的不同专业，不同年级的，都是多对多的关系。」**

推论（这是设计约束，不是猜测）：

```
自然人 person ─┬─ 平台账号 account（超星 1..N、新站 1..N）     ← 一人多号
              └─ 学籍/机构 enrollment（学校 × 专业 × 年级）      ← 一号多学籍、一学校多专业
```

- **不是"给 `accounts` 加一列 `platform`"就能解决**：真实关系是 `person ↔ platform_account ↔ (school, major, grade)` 三层多对多。
- **面板要做"跨平台统一视图"**：展示按 **人** 聚合，调度按 **账号** 执行。
- **画像不能按学校聚合**：现有画像字段假设"平台给姓名 + 学校"（超星），新站同一人可能属于多个学校/专业/年级 → 画像主键必须是 `(person, platform, school)` 三元组。
- **防双开约束的粒度要说清**：超星的"单账号单进程单会话"是**账号级**；一人两平台两账号**不算**双开，但同平台两账号同时跑必须禁止。

**现在的动作**：**超星主线一行代码都不改**（避免为未开工的项目预埋风险）。只在 §七 登记"开工第一天要做的数据模型设计任务"，让它成为 `feat/gxks` 的第一个 PR，而不是中途返工。
