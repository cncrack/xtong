### 2.3 计时与续播机制（第三方行为描述，尚无本轮实测）

> ⚠ **本节已被 2026-10-29 实测部分推翻**：计时确实是“按时间累计、倍速无效”，但**不是“服务器时钟同步”**、**也不是“按课程表分钟数 seek 续播”**——真实实现见 **§2.10**。本节保留作历史对照。

> 下述倍速、心跳、seek 与刷新行为不作为本项目的执行指令；播放和调速均须取得授权后核实。

- `#spTitle` 显示**服务器同步时间**；上游脚本每 60 秒读它，**两次内容相同就判定"数据同步异常"→ 刷新页面**。
- 含义：**服务端按自己的时钟累计学习时长**，与客户端 `video.currentTime` 推进多少无关 →
  **倍速播放无效**（上游 README 也明写"观看进度按实际时间计算，无法倍速"）。
- 续播：从课程表的「已学 X 分钟」解析出分钟数，直接 `video.currentTime = X * 60` 跳到未看部分。
- 视频事件：`onended` → 刷新继续下一个；`onpause` → 1 秒后重试 `play()`；`onerror` → 刷新；加载检查计数器到 8 次仍无视频 → 刷新。

### 2.4 题库机制（与我们的 AI 作答对照）

- 题库存浏览器 `localStorage`，key 为 `题库`，结构 `{ 题干文本: [答案文字...] }`。
- 题干由正则 `/\d+\.(.*)\(/` 从题目 `dt` 文本截取（**只取到左括号前**）。
- 答题页：命中题库则按选项文字匹配并 `click()`；未命中跳过。
- 交卷后自动进 `viewexam`，读 `.green` 标色内容回收正确答案入库（判断题会把 `对/正确`、`错/错误` 都写进答案数组，选择题按 A~H 字母反查选项文字）→ 这是上游行为描述，**本项目不为采样反复考试**，`.green` 是否正确答案仍待历史答卷证实。
- 跨 iframe 协作：答题页写 `localStorage.examAction = done:<时间戳>`，交卷框架 5 秒内看到该标记才交卷。

| 10 | `disable.js`（3382 字节）= 禁右键 / 禁选择 / 屏蔽 F12 与 `Ctrl+*` 等快捷键，**纯前端事件拦截、不上报任何数据** | 与自动化无关；对 CDP 无影响，它连 DevTools 都拦不住 |
| 11 | 播放页**无** `webdriver`/`phantom`/指纹 SDK/摄像头/截图/鼠标键盘活跃度判定；无 `beforeunload` 拦截 | 不要求“人在动鼠标”；但**要求页面在前台**（见 #6） |
| 12 | 负向对照：**打开播放页不点播 5 分钟 → 学时 0、「未学习」**；点播放 4 分钟 → 「学习中」；约 7 分钟 → 「已完成学时 10 分钟」 | ① “打开≠学习”成立，挂页面拿不到学时；② 学时**不少于**真实播放时长（10 ≥ 7.2），疑有取整或双计 → **具体口径待 T4 单条干净复测**，此处不下结论 |
| 13 | **第三方资源清单（抓包全量域名统计）**：`g.alicdn.com`（Aliplayer 2.9.11 主库 + `vod`/`hls` 插件 + 皮肤 CSS，**HTTPS，官方 CDN**）、`vod.gaoxiaokaoshi.com`（阿里云 VOD 加速域，m3u8/ts 分片）、`videocloud.cn-hangzhou.log.aliyuncs.com`（Aliplayer 内置埋点 `POST /logstores/newplayer/track`，一次会话 **21 次**）。页面自身内联脚本 **零** `log`/`track` 代码 | ① 库内容**站点改不了**（官方 CDN + HTTPS，比逐行读代码更硬的证据）；② 但**播放行为被阿里云侧统计**，而 VOD 域名属站点自己的阿里云账号（【推断】）→ 站点后台可见播放质量/行为报表；③ 这是**被动统计**，不是客户端拦截 |
| 14 | **媒体元素周期性重建并非反刷**：`blob:` URL 每次不同、`currentTime` 归零、瞬间 `paused=True/rs=0/d=None`，但**计时链照走** | 若真为反刷，必须配合“停表 / 要求交互”才拦得住任何东西；而站点计时本就不读 `currentTime`，也就没有动机保进度连续 → 巡检看到“进度归零”**不要修**（不 seek 回去、不重 play，后者会触发多条计时链） |
| 15 | 重建与前导缓冲相关：重建前 30 秒普遍出现 `rs=2`；`m3u8` 播放列表每 7~13 秒刷新一次 | 归因为 HLS 内核的**卡顿自恢复**（detach/attach → 新 MediaSource → 新 `blob:`）；**具体机制未证实**，但不影响我们的判据（判据只看 `paused` 与上报节奏） |
| 16 | 页面里 `seek` **只有 1 处用途**：`myload()` 首次 play 时读续播 cookie 并 `player.seek()`（`_init==0` 只执行一次）——**断点续播，不是防拖拽** | ① 我们仍不 seek（纪律）；② 技术上**拖到末尾也不能加速学时**（计时是墙钟、与进度无关）→ 这正是站点不需要检测拖进度的原因 |
| 17 | ⚠ **页面学时与服务端列表学时严重不一致**：同一时刻页面 `spTitle`「此次学习/累计 **51分11秒**」，而列表「已完成学时」只有 **27 分钟**、状态仍「学习中」；与早前「播 7 分钟→列表显示 10 分钟」（偏**大**）方向相反 | 列表列名写的是「已完成学时」，但口径非墙钟 → **达标判定只能取列表值**（C4）；具体口径待单节干净复测（Q8）。不要用页面 `spTitle` 推算达标 |
| 18 | 媒体重建**实测两次但签名不同**：6m00s 重建为 `paused=True`，28m30s 重建为 **`paused=False`**；两次间隔 22.5 分钟 | 巡检识别重建**不能看 `paused`**，要看 `duration=None` + `readyState=0` + `blob:` 变化（方案侧 C7 已改） |

**结论边界**：本节只证明「播放页没有主动的机器人/指纹检测代码」，**不等于站点不检测**——服务端仍可按上报节奏、时间间隔、IP、并发形态做行为判定。因此实现侧必须**正常播放**：不得伪造 `updateTime` 请求、不得反复 `play()` 拖快计时、不得拖进度。

> 关于“要不要逐行读 Aliplayer 那几 MB 压缩代码”：**不读**。理由：① 来源是官方 CDN 的 HTTPS 资源，站点无法改其内容，读它只能读到“官方播放器怎么工作”；② 我们的判据不依赖库内实现，只依赖三个可观测量（`video.paused`、`video.currentTime` 是否推进、`updateTime` 是否每 60 秒出现）；③ 真正做判定的是**服务端**，前端代码里永远读不到那个阀值。

## 四、开工时必守的约束与红线

**安全（历史入口为 HTTP，登录前重新核实）**

1. 凭据只走 `core/crypto.py`（AES-256-GCM）落盘，绝不进 `settings.toml` / 代码 / 文档。
2. 日志与事件**不打印任何凭据与 cookie**（`scripts/push_check.py` 敏感扫描覆盖此项）。
3. **不在公共网络 / 不明 WiFi 登录**；自有网络和本地加密也不能消除 HTTP 传输风险。先核实 HTTPS、重定向和表单提交目标；仍仅 HTTP 时须告知凭据风险并由用户决定是否继续，禁止忽略证书错误或在聊天收集密码。

**实现红线（上游能跑 ≠ 我们对）**

1. **绝不全局劫持 `window.confirm/alert`**。上游用 `Object.defineProperty(..., {writable:false, configurable:false})` 让 `confirm` 恒返回 true 来"不被弹窗卡住"——若平台用 confirm 确认"确实交卷？"就是**误交卷**。我们处理弹窗必须显式 accept/dismiss **并写事件记账**。
2. **自愈不得退化成 `location.reload()` 循环**（会丢定时器状态）。用我们已有的 `runmark` + 事件记账 + 四档状态机（Q19）。
3. **登录页匹配用正则包含式** `login\w*\.aspx`，不要硬拼文件名 —— 上游用 `pathname.indexOf('login.aspx')`，**匹配不上真实入口 `loginb.aspx`**（照抄别人的匹配值就是坑）。
4. **题库 key 用 `question_hash`（sha256(题干+选项)），不用题干原文** —— 上游 `bank[题干]` + 截断正则，题干标点/空格一变就 miss。
5. **必带低频拟人化**：`pace` 三档间隔 + `daily_max_minutes` 额度 + 每日窗口。上游是零间隔、零额度、零并发控制（`onpause` 后 1 秒立即 `play()`、`volume=0`、全天可跑），这恰好是风控最典型的机器人形态。
6. 平台细节只写在 `src/xxt/adapters/gaoxiaokaoshi/` 内；新站所需核心解耦先在独立分支实现，不先改超星。Q27 不作为本轮统一阻塞；现行准入见 `PLAN-GXKS.md` §二。
7. **不得访问 `admin/` 与任何越权路径**（A 级实测：普通账号页面里就藏着 `../admin/Default.aspx`，只是 `display:none`）。隐藏≠授权；任何会话/代码**不得尝试请求 admin 路径**，也不得拿别人的学号试登录。

## 七、特征检测与封号风险（2026-10-27 公开页历史观测，结论边界已修正）

### 7.0 本次做了什么（合规声明）
只 GET **公开页**（`/`、`Loginb.aspx`、`MainPage.aspx`、`Default.aspx`、`Login/Loginm/Loginp.aspx`）与它引用的 3 个 JS；**无凭据、不填表、不提交、不登录**；每 URL ≤4 次尝试带随机间隔。第一轮（21:05）约 10 个请求，第二轮（21:40，回答“login.aspx 能否用”）约 20 个请求。探针：`data/debug/probe_gxks_{loginb,headers,pages,js,login_aspx,redirect}.py`（不入库），产物 `data/debug/gxks_html/`。

### 7.1 结论边界：旧样本未检出常见检测代码，不代表零检测

| 检测面 | 命中 | 判读 |
|---|---|---|
| 自动化检测（`webdriver`/`phantom`/`selenium`/`headless`/`$cdc_`）| **无**（三页 HTML + `Login.js` 6555 字符 + `index.js` 1852 + `Dialog.js` 27830 全扫零命中）| 只能说明当时检查的样本未命中这些字符串 |
| 指纹采集（canvas/webgl/plugins/toDataURL）| **无** | 未命中不等于没有其他形式的采集 |
| 埋点上报（beacon/cnzz/umeng/gtag）| **无** | 未见所列第三方分析标识；不能排除自有上报、动态加载或网络层观测 |
| `navigator.userAgent` | ① `Dialog.js` 判 `isIE/isIE6/isGecko`（老式兼容）② ⚠️ **`Default.aspx` 内联脚本用 UA + `screen.width` 做入口分流**（2026-10-27 21:40 第二轮补测发现，修正我先前“仅 Dialog.js”的说法）| 两处都**不是反爬/指纹**，是 2010 年代的浏览器兼容分支；但**后果是硬的**：Edge 被 `alert` 拒进、移动端 UA 被踢到结构不同的 `Loginm.aspx`。详见 §7.4 |
| `window.onerror = function(){return true;}` | loginb 内联 | 吞 JS 错误（老站常见），不是检测 |

**撤回旧绝对结论**：“客户端零检测、风控全在服务端”“不会因为被识别为脚本而封号”均无充分证据。静态字符串检查覆盖有限，不能排除动态脚本、其他页面、网络层与服务端检测，也不能承诺不会封号。

### 7.2 服务端暴露的两处风控痕迹 ⭐ 本次最重要的发现

1. **`Loginb.aspx?needVerify=1` = 可升级的验证码闸门**
   页面上是 `<tr id="trVerify" style="display:none">`，末尾脚本 `if(location.search.indexOf('needVerify=1')>-1)` 才把它显示出来；验证码图 = **`VerifyCode.ashx`**（服务端生成 4 位，`maxlength=4`，点击刷新 `?t=Math.random()`）。
   → 只确认历史样本中该参数控制验证码显示；**触发原因、是否必然与可疑判定相关、是否存在其他提示均未知**。撤回“封号前最后一道闸门”“唯一可见信号”的推断。
   → **设计定论**：adapter 必须识别 URL 上的 `needVerify=1` 并**立即停止自动登录、转人工**，绝不自动试错验证码（连续试错 = 撞库特征，最危险）。
2. **密码明文 POST、无客户端哈希**
   `CkeckNotNull()` 仅做非空校验，然后 `document.getElementById("frmLogin").submit()`；字段 = `name` / `pw` / `verifyCode` / `screenType`（hidden，值 `1440` 为服务端渲染）；表单 `action="HidLogin.aspx" method="post"`。
   → 没有任何“客户端加密指纹”需要复刻（好事：实现简单；坏事：明 http 下凭据完全裸奔，见 §四）。

### 7.3 站点稳定性：间歇 503（**推翻我 20:10 的判断**）

实测：root 第 1 次 503；loginb 第 1 次 **`RemoteProtocolError`（收到 1139/2785 字节被对端截断）**、第 2 次 503、第 3 次 200；mainpage 直接 200。**同一 URL 换 UA 结果相反**（`/` 空 UA 时 503、`Loginb` 空 UA 反而 200）→ 是随机而非按 UA 判定；响应为**空 body、无拦截页、无 `Retry-After`、无 WAF 头**（`Server: Microsoft-IIS/10.0` + `X-ASPNET-Version: 4.0.30319`）。

🔴 **自纠（第二次）**：20:10 我根据“两次抓取为空 body”断言“服务器对非浏览器不给内容 → `httpx` 直取不成立，必须真 Playwright”——**错了**，那是撞上间歇 503。
但 21:40 第二轮又发现：**我把“httpx 能取到页”这件事对登录页说得太满了一半**——登录页对 HTTP 直取**根本不给表单，只给 `302 → /Default.aspx`**（见 §7.4），前几轮之所以“一会儿 200 拿到表单、一会儿 302/503”，不是服务器抽风而是**撞在跳转门上**。
→ 修正后的分层（这是最终版）：**静态/内容页可走 `httpx`（带重试）；登录与登录后的业务页统一走真浏览器**——因为在浏览器里 `Default.aspx` 的分流 JS 会自动完成，而纯 HTTP 要自己复刻“解析 JS 分流规则 + 按屏幕宽度选页 + 处理 302”，不划算且易出自洽破绽。工作量按这个分层重估（§0.2 定的人天仍不立刻下调，因为登录后的页面还未实测）。
→ **边界修正**：观测到 503/截断，但仅凭空 body、缺少 WAF 头或少量 UA 对比不能确定原因，也不能排除风控。遇此类响应有限退避，不绕过、不反复请求来判断阈值。

⚠ **2026-10-30 补充：另一类 503 来自本机，不是站点**。用户点「参加练习」后连续 `chrome-error://chromewebdata/`，一度怀疑时间不对。双向计时探针找到真因：系统代理 `127.0.0.1:10808`（v2rayN / xray，全局模式）把国内站点绕到境外节点，**单次请求 24 秒**（`Login.aspx` 直连 279ms / 走代理 23517ms，慢 80 倍）→ `ExamCreate.ashx` 写库超时。清除系统代理后 `ProxyEnable=0`、直连 323ms，故障消失。

⇒ 排查顺序应固定为：**先验本机出口（直连 vs 代理计时对比）→ 再看页面错误码 → 最后才怀疑站点**。对刷课影响更大：`updateTime.ashx` 每 60 秒上报一次，每次拖 24 秒会让上报节奏崩掉、学时真丢，**刷课前必须确认该域名直连**。

### 7.4 登录形态与跳转链（原 A2/A3 已全部答完，A 级）

**凭据形态**（用户 2026-10-27 确认：“**学号加密码，没有看到图形验证码**”）：

- **学号 + 密码 + 可选图形验证码**；**无手机号/短信验证码**（页面文本只有「账 号 / 密 码 / 验证码 / 忘记密码？」，无“手机”“学籍”“身份证”字样）
- 用户“没看到验证码”与实测完全吻合：`trVerify` 默认 `display:none`。**但“没看到”≠“没有”**——何时出现仍未知（§7.2）
- `Login.js` 函数表里有 `isEmail` / `chkExitsEmail` / `check_username` / `chkRegInfo` / `frmReg` → 平台支持自助注册（但用户说实际用**学号**，以用户为准）

**入口分流链（谜底：`b` = big screen）**——直接 GET 任何一个登录页，得到的都是 `302 → /Default.aspx`（**不带 ReturnUrl**；业务页如 `Main.aspx`/`LoginA.aspx` 则是 `?ReturnUrl=…`），而 `Default.aspx` 本身是个**纯 JavaScript 分流器**：

```js
_pass = !isEdge;                       // Edge 直接弹 alert 拒进
if (isipad)                 location.href = "Loginp.aspx";
if (bIsIphoneOs||bIsAndroid) location.href = "Loginm.aspx";
if (screen.width < 1400)     location.href = "Login.aspx";    // 小屏版
else                         location.href = "Loginb.aspx";   // 大屏版
```

- 因此 `Login.aspx` 与 `Loginb.aspx` **是同一张表单的两个宽度版本**（字段同为 `name`/`pw`/`verifyCode`/`screenType`），不是教师端/管理端——**A3 作废**
- 我们的 1440×900 正好落在 `Loginb` 那一支，**与用户平时看到的入口一致**（一致本身就是拟人）
- ⚠️ **`screenType` 自洽要求**：表单里的 hidden `screenType` 是屏幕宽度档位，必须**与真实视口一致，绝不硬编码 1440**；不自洽（例如报 1440 却走 `Login.aspx`）是我们自己造的破绽
- 用户原问“不知道暗地里有没有其它指纹特征”→ 历史样本未检出常见设备指纹代码，已见 UA/分辨率分流；完整检测能力仍未知，只观察正常授权操作，不测试风控底线

### 7.5 保守操作建议（不能保证不封号；实施范围见治理方案）

| # | 对策 | 理由 |
|---|---|---|
| 1 | 禁止同一账号多开；**本轮核实仅一个新站浏览器会话** | 多账号是后续需求；旧“2 账号/同 IP 砍半”不是实测安全阈值，现行规则见 `PLAN-GXKS.md` §7.3 |
| 2 | `pace` 三档间隔 + `daily_max_minutes` + 每日窗口全带，**新站额度从超星的 50~70% 起步** | 服务端按自己的时钟计时，“一天刷满 10 小时”直接写在它的库里 |
| 3 | **撞 `needVerify=1` 即停并转人工**，禁止自动试错验证码 | 验证码出现即转人工；触发原因与后果未知，不主动诱发或绕过 |
| 4 | 单账号单进程单会话（沿用超星地基），锁粒度是**账号**不是“人”（一人两平台两账号不算双开）；会话失效走 `relogin` 且**每日登录次数有预算** | 多端并发/频繁重登是最典型机器人特征 |
| 5 | 503/截断按“服务不稳”处理：上限 3 次 + 指数退避 + 随机抖动（复用 `retry_jitter_pct`/`retry_max_minutes`）| 避免重试本身成为异常行为 |
| 6 | 只在**自有网络**登录；凭据走 `core/crypto`；日志零凭据零 cookie | 本地加密不能补偿 HTTP 传输风险；仍需登录前风险确认 |
| 7 | **不逆向 `HidLogin.aspx` 直接 POST 登录**（即使技术上可行）| 绕开正常流程是最强机器人特征，且明 http 下凭据更暴露。“后期是否还需要逆向”用户 2026-10-27 定为**待辨别**→ 见 `PLAN-GXKS.md` D11：默认不逆向，不预先解析 viewstate，到开工二次核实时再判 |
| 8 | **UA 固定普通 Chrome 桌面版**：绝不 Edge、绝不带移动端/平板标记 | Edge 被 `alert` 拒进（在 Playwright 里还会弹一个阻塞对话框）；移动端 UA 会被分到 `Loginm.aspx`，结构完全不同→选择器全失 |
| 9 | **视口宽度固定 ≥1400**（沿用 1440×900），`screenType` 取真实视口值而非硬编码 | 低于 1400 会换一张表单；`screenType` 与视口不自洽 = 自己造破绽。⚠ **现状冲突**（本轮读代码发现）：超星 `core/stealth.py:83-84` 固定 `viewport/screen = 1280×800`，**照搬这套参数新站永远进不了 `Loginb.aspx`** → 必须落实为 `PLAN-GXKS.md` §7.1 的 `[driver] viewport="match_screen"`，不能停在本文档 |
| 10 | 登录路径**只走浏览器**（`Default.aspx` 分流器自动完成），不用 httpx 手拼 302 链 | 见 §7.3 修正：手拼要复刻分流规则，易错且留不一致痕迹 |
